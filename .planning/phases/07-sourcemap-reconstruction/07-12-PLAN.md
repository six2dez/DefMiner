<objective>
Widen `source_sightings`' primary key so a second bundle carrying the same map keeps its own evidence,
and retire the interim guard that was standing in for this.

This closes verification finding **W-3** and code-review finding **HI-03** completely. The shipped
interim guard stops bundle A's sightings being stolen; it does not stop bundle B's being lost, and
the shape of B's loss is the problem: B's drill-down reads a **resolved zero** on the one column whose
entire design is that a resolved zero cannot lie.

Purpose: `(project_id, map_sha256, source_index)` → `(project_id, artifact_sha256, map_sha256,
source_index)`. `map_sha256` is content-addressed over the decoded map JSON and never over the bundle,
so two bundles can share it at the target's discretion — a CDN mirror with a different banner comment
is enough. The key must span the bundle for the row to be about the bundle.

Output: migration `v: 9`, a fifth one-way `EXPECTED_TABLES` approval, a four-column conflict target,
and the removal of the interim mitigation and its counter.

**This plan is `autonomous: false`.** Task 1 is a `blocking-human` checkpoint and no migration may be
written until it is answered.
</objective>

  <decision>
Changing a shipped primary key is a ONE-WAY door on the same terms adding a table is:
`schema.spec.ts` asserts the table set exactly, the migration ladder is forward-only, and operators
have real rows in these tables today. FOUR prior approvals are recorded in `EXPECTED_TABLES`'s own
comment; this is the fifth and must be named there too.

**Why this is being asked for.** `source_sightings` is keyed `(project_id, map_sha256, source_index)`
and `map_sha256` is content-addressed over the DECODED MAP JSON, never over the bundle. Two different
bundles can therefore share a `map_sha256` — a CDN mirror with a different banner comment, a decoy
stub carrying a copy of the map, or the same library genuinely re-bundled. Plan 07-05's shipped
interim guard stops the second bundle OVERWRITING the first bundle's attribution, and counts the
discard. **It does not give the second bundle its evidence back.** Bundle B's drill-down reads a
RESOLVED ZERO and the tree says "No recovered sources in this bundle" — on the one column whose whole
design is that a resolved zero and an unresolved count are different facts that must never be the same
pixel. It is target-triggerable at will.

**The proposal, stated in full before the migration is written.**

`EXPECTED_TABLES` keeps its EIGHT members and the array is byte-unchanged:

`["analyses", "artifacts", "audit", "observations", "scans", "settings", "source_sightings", "sources"]`

**No table is added. No column is added, removed or retyped.** The change is one line of DDL.

`source_sightings` PRIMARY KEY, as it ships today:

`PRIMARY KEY (project_id, map_sha256, source_index)`

`source_sightings` PRIMARY KEY, as it would read after this step:

`PRIMARY KEY (project_id, artifact_sha256, map_sha256, source_index)`

Every other line of that table's DDL is unchanged: the same ten columns, the same types, the same
`CHECK` constraints, the same closed producibility vocabulary, `project_id` still at PK ordinal 1.

**The two column lists this touches, in full.**

`source_sightings` — ten columns, none changing:

| Column | Type | In the new PK? |
|--------|------|----------------|
| `project_id` | `TEXT NOT NULL CHECK (length(project_id) > 0)` | yes, ordinal 1 |
| `artifact_sha256` | `TEXT NOT NULL CHECK (length(artifact_sha256) = 64)` | **yes, ordinal 2 — this is the change** |
| `map_sha256` | `TEXT NOT NULL CHECK (length(map_sha256) = 64)` | yes, ordinal 3 |
| `source_index` | `INTEGER NOT NULL` | yes, ordinal 4 |
| `request_id` | `TEXT NOT NULL` | no |
| `source_sha256` | `TEXT` | no |
| `sources_verbatim` | `TEXT` | no |
| `producibility` | `TEXT NOT NULL CHECK (producibility IN ('producible','gone','changed'))` | no |
| `producibility_at` | `INTEGER` | no |
| `recovered_at` | `INTEGER NOT NULL` | no |

`sources` — five columns, **entirely untouched by this step**: `project_id`, `source_sha256`,
`byte_len`, `line_count`, `first_seen_at`, PRIMARY KEY `(project_id, source_sha256)`. Content-addressed
dedupe across bundles is exactly what that table is for and this change does not weaken it.

**Migration version: `v: 9`.** `SCHEMA_VERSION` is derived from the last step and becomes 9 without
being restated anywhere.

**How the step runs, because SQLite cannot alter a primary key in place.** It is a table rebuild in
step `v: 7`'s exact shape — the one this repository already litigated when it widened `audit`'s CHECK:
create `source_sightings_v9` with the new key, `INSERT OR IGNORE ... SELECT` every row across, drop
the old name, rename, recreate the index. `source_sightings_v9` is transient and never an
`EXPECTED_TABLES` member, the same way `audit_v6` is not.

**No row is lost by the copy.** Every existing row has a distinct `(project_id, map_sha256,
source_index)`, so it necessarily has a distinct `(project_id, artifact_sha256, map_sha256,
source_index)`. The copy cannot conflict and `OR IGNORE` never has anything to skip.

**What is irreversible, stated plainly.**
1. **The ladder is forward-only.** Undoing this is another forward step that rebuilds the table again
   under a narrower key — and that step WOULD lose rows, because two bundles' sightings collapse onto
   one key going back.
2. **The published identity changes.** A sighting's identity becomes "this bundle's view of this map
   at this index" rather than "this map at this index". Anything later that reasons about sightings —
   Phase 8's active probe, v2's DIFF-01 cross-deploy diffing — inherits the wider identity.
3. **`schema.spec.ts` pins it.** The shipped key becomes the asserted key, so a future narrowing fires
   the gate by design.

**What this does NOT do, so the approval is not read wider than it is.** No foreign key. No
`ON DELETE CASCADE`. No content column. No new table. The eviction cascade for these two tables is a
SEPARATE piece of work (plan 07-13), deliberately built as an anti-join rather than an FK precisely so
it needs no schema change and no sixth approval.

**The cost, restated so the approval is informed.** Row volume goes UP for the duplicated-map case,
which is the point: where the interim guard wrote one set of sightings for two bundles, this writes
two. D-09's accepted cost — one row per recovered source under the NORMAL retention caps, no exemption
— now applies per bundle. A 781-source map seen in two bundles is 1,562 `source_sightings` rows rather
than 781, against a `DEFAULT_RETENTION_MAX_ROWS` of 50,000. The `sources` table does NOT double,
because it is keyed on content.

**What becomes dead on the day this lands**, and is removed in the same plan rather than left to rot:
the interim attribution guard (a predicate that can no longer be false, since `artifact_sha256` is a
key column) and the `sightingsDiscardedOtherArtifact` counter (a number that can no longer be
non-zero). That counter's own docblock already says it "goes to zero when the v9 key widening lands".
