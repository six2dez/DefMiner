<objective>
Build the deployment matrix DEPLOY-01 asks for, as re-runnable evidence rather than as memory.

Purpose: DEPLOY-01 names four shapes — local desktop, remote command line, and Docker both with and
without a persistent volume — and the property DEPLOY-02 and DEPLOY-03 exist because of is that the
server's disk is not the operator's. On one machine the desktop and command-line legs SHARE a
filesystem, so only the container legs genuinely exercise that property. The harness says so in its
artifacts rather than reporting four independent confirmations of something two of them test.

Output: `scripts/phase6/matrix-leg.sh`, `scripts/phase6/matrix.sh`, a sibling result schema, and
`tests/phase6-matrix.spec.ts` — plus one recorded run of every leg that can run on this machine.

**The measured facts this plan stands on**, all established in research rather than assumed: the image
declares no volume, so an unmounted container's data lives in the writable layer and dies with the
container; the registry publishes the same version tag as the desktop build, so the matrix is
internally version-consistent across all four legs; and the image carries a native manifest for this
machine's architecture, so the documentation's architecture advice is stale and must not be inherited.
</objective>
