<objective>
Harden the one place operator input meets a query language, and build the gate that keeps it the only
place.

Purpose: D-05 promises the operator may narrow and never widen. Caido's HTTPQL reference contradicts
itself on AND/OR precedence on a single page, and HTTPQL supports both `//` and block comments — which
means an operator clause placed before DefMiner's could comment DefMiner's narrowing away. Full
parenthesisation makes the meaning independent of which precedence reading is true, and operator-last
ordering turns the comment attack into an unbalanced expression that `execute()` throws on. And
`sql-discipline.spec.ts` cannot help: its sink set is `prepare`, `exec`, `run`, `get`, `all` and its
`looksLikeSql()` requires a SQL keyword, so it is silent here by construction rather than by oversight.

Output: `validateOperatorClause` with its closed rejection vocabulary, the hardened `composeScanFilter`,
and `packages/backend/src/scan/httpql-discipline.spec.ts` — a static AST gate in
`sql-discipline.spec.ts`'s exact shape.

**The reframing worth holding on to:** a widened HTTPQL clause cannot produce a row that `admit()`
would reject, because `admit()` runs on every returned item regardless and its fifth axis is Caido's
own scope engine. The push-down is an OPTIMISATION, so the risk it carries is COST, not correctness —
a widened clause turns a targeted scan into a pull of every stored body in history on a runtime where
every page transfers full bodies. Framing this gate as a cost control rather than a correctness
control is what makes it easy to write and easy to defend.
</objective>

  <action>
Add `OPERATOR_CLAUSE_MAX_CHARS` and a closed `OPERATOR_CLAUSE_REJECTIONS` array — members
`comment_construct`, `unbalanced_parentheses`, `whitespace_only`, `too_long` — with
`type OperatorClauseRejection` derived from it in the `REJECT_REASONS` idiom. Export
`validateOperatorClause(raw: string): { ok: true } | { ok: false; reason: OperatorClauseRejection }`.

The four checks, in this order, each with its reasoning written beside it:

1. **Comment constructs.** Refuse any occurrence of the line-comment marker or either block-comment
   marker. DefMiner has no use for an operator comment, and a comment is the one construct that can
   reach across a parenthesis. Detect them by index scanning, NOT by regular expression — the
   admission path's no-regex prohibition is a project rule and ReDoS is unrecoverable on this runtime.
2. **Parenthesis balance.** A simple depth count that skips characters inside double-quoted strings,
   with the escape convention handled. Refuse a negative depth at any point and a non-zero depth at the
   end. A clause whose parentheses balance only inside a string literal is a legal clause and must be
   accepted — that case is the reason the counter is quote-aware rather than a naive tally.
3. **Whitespace-only.** Refuse rather than normalise. Composing without the third term is the correct
   handling of an ABSENT clause; a clause the operator typed and that means nothing is a mistake worth
   naming, and the copy for it is already written.
4. **Length.** A declared cap, exported so the spec asserts against the constant and the frontend's
   input renders within the same number rather than a second copy of it.

Harden `composeScanFilter` to take the validated clause and keep the contract explicit in the header:
DefMiner's clauses FIRST, the operator's LAST, every clause individually parenthesised. Quote the
precedence contradiction in the header — the reference's "Both have the same priority" box and its
worked examples two paragraphs below stating that AND binds tighter — so a later reader can see the
composition is a derivation and not a style preference.

Keep the kind clause on the case-insensitive `cont` family. Write out, term by term, why the five
`resp.raw` substrings cover all seventeen `SCRIPTISH_MEDIA_TYPES` essences, and why `req.ext.eq` is
excluded: it is documented case sensitive while `isScriptish` lowercases before its suffix test, so
that one term would break the superset relation on an uppercase path. Note that `resp.raw` matches
the body as well as the headers, which over-matches in the SAFE direction, and that plan 06-11's
fixture suite is what proves the superset relation rather than this comment.

`filter.spec.ts` covers every behaviour above, plus the mechanical assertion that every member of
`OPERATOR_CLAUSE_REJECTIONS` is exercised — the shape `admit.spec.ts` uses for `REJECT_REASONS`.

**Open with the why-static argument, in the parent's voice.** Every failure mode this gate covers is
