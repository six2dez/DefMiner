<objective>
Ship the PROOF that DefMiner writes nothing to server disk, and the proof that no column can hold the
content it would otherwise write.

Purpose: `HostedFileSDK` is exactly `getAll()` and `create({ name, content })` — verified against the
newest published SDK, not merely the pinned one. **There is no delete and no expiry.** DEPLOY-03 asks
for "expiry and redaction rules" and DEPLOY-04 for "orphan cleanup"; neither is expressible against
that surface, and a hosted file, once created, is permanent and unreclaimable. DEPLOY-03's own wording
offers "**or** a bounded authenticated frontend download" as an equal alternative, and Phase 5 already
built and measured exactly that.

So DEPLOY-03 is met by its own alternative wording, and DEPLOY-04's normative statement — treat server
disk as shared instance storage — is discharged by writing nothing to it. What ships is not machinery;
it is the two gates that keep the guarantee true, so the day someone adds a filesystem import or a BLOB
column the gate fires and the decision is re-opened deliberately.

This is the same move this project made for the pre-policy observation-URL population: prove the branch
is unreachable rather than shipping a sweep for it.

Output: `packages/backend/src/filesystem-prohibition.spec.ts` and D-24's declared-type check in
`schema.spec.ts`.

**Stated rather than compensated for:** the ROADMAP's plan title for this area —
`06-03: Hosted-file delivery, quotas, orphan cleanup, and storage labelling` — describes four things,
three of which D-17 makes impossible or unnecessary. The ROADMAP's plan list is amended alongside this
plan set. If this plan feels thin against that title, that is D-17 working, and `06-CONTEXT.md` asks
that it be said rather than padded back out.
</objective>

  <name>Task 1: One-way decision — the RPC download is the only delivery path, and the hosted-file surface is declined (D-17)</name>
  <decision>
    Phase 5's D-04 is extended project-wide: the chunked RPC download is the ONLY path by which
    anything DefMiner produces reaches the operator, nothing is ever written to server disk, and
    Caido's hosted-file surface is explicitly DECLINED and made unreachable by a static gate.
  </decision>
  <context>
    **Reversibility: one-way.** Undoing this means introducing a filesystem module, a labelled server
    path, disk quotas, orphan cleanup and hosted-file delivery; lifting a shipped source-level ban; and
    re-opening Phase 7's storage design. The Deferred Ideas register already records that the
    quota-and-cleanup machinery comes back as a SET if it comes back at all, not piecemeal.

    Three facts drove it:

    1. `HostedFileSDK` is `getAll()` and `create({ name, content })` and nothing else — verified this
       research session against `@caido/quickjs-types@0.26.0`, confirmed the latest published version.
       No delete, no remove, no expiry, no TTL. Note also that `HostedFile` carries a server `path`,
       which displaying would violate both the storage-labelling rule and D-19.
    2. DEPLOY-03's own text offers a bounded authenticated frontend download as an equal alternative,
       and Phase 5 shipped and measured it: `packages/backend/src/store/export.ts` plus
       `packages/frontend/src/components/export-download.ts`.
    3. If reconstructed source is content-addressed and never used as a filesystem path, Phase 7's
       hardest requirement — SC3's malicious-`sources` traversal / UNC / drive-letter / reserved-name
       fixture suite across three platforms — stops having a subject.

    **The dependency this decision has and does not discharge.** D-17's long-run viability rests on
    **O-01**: can Phase 7's reconstructed source live in SQLite within QuickJS's memory? The research
    argues the memory question does not discriminate between the two designs — `JSON.parse` of the
    whole map materialises every source entry before either a database bind or a file write, so files
    do not avoid the peak — but that argument is REASONED, not measured, and this runtime exposes no
    memory introspection at all. O-01 is recorded as a named carried obligation owned by Phase 7's
    first plan, with the external-RSS probe named as its discharge. **If that probe is negative,
    Phase 7 re-opens D-17 deliberately rather than working around it.**

    **Consequences, all intended:** DEPLOY-03 is met by its own alternative wording; DEPLOY-04 loses
    its file subject and is met by construction plus D-24's gate; DEPLOY-02's subject becomes the
    database rather than a file; and ROADMAP Phase 7's stated dependency on a Phase 6 delivery path is
    already satisfied by shipped Phase 5 code.
  </context>
  <options>
    - **Approve as specified** — decline the hosted-file surface, ban the filesystem at source level,
      and carry O-01 as a Phase 7 obligation.
    - **Approve, but defer the source-level ban** — the guarantee becomes a promise rather than a
      gate, and DEPLOY-04's "what ships is the proof" is not delivered.
    - **Reject** — hosted-file delivery is built, and with it a delivery path with no delete and no
      expiry, plus the quota and orphan-cleanup machinery DEPLOY-03/04 ask for and the SDK cannot
      support.
  </options>
  <recommendation>Approve as specified. It is the option that minimises permanent, unrecoverable state — the same call the operator made on every Phase 5 decision — and O-01 is carried openly rather than assumed away.</recommendation>
