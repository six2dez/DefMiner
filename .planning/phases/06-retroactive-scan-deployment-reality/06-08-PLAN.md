<objective>
Make DEPLOY-02 true by SUBTRACTION plus three counts, and add the one honest persistence sentence the
SDK can support.

Purpose: D-19's core sentence already ships — `settings-contract.ts` exports a storage note stating
that DefMiner's database lives on the Caido server, not on this machine, and it renders
unconditionally. What Phase 6 owes is the removal of the path machinery around it, the row counts
beside it, and the disposal of Phase 5's outstanding `behavior_unverified` item.

**Do not design a surface that already exists.** If this plan feels thin against the roadmap's original
ambition for hosted-file delivery and storage labelling, that is D-17 working, and `06-CONTEXT.md`
asks that it be stated rather than compensated for.

Output: five exports and one prop deleted together with their five spec cases; three footprint rows;
and a boot marker that lets the persistence sentence be an observation instead of a guess.

**The O-02 disposition this plan takes, and why.** The backend can learn essentially nothing about
persistence from introspection: the SDK's complete member list carries a version string and two server
path strings and no durability signal of any kind, the OS module has no hostname accessor, the process
global does not load, and the container marker file is unreachable under D-18 by construction — and
would only distinguish container-from-not, never volume-from-no-volume. But persistence is not an
introspectable property; it is an OBSERVED one. A durable marker written at first `init()` and read
back on every subsequent one turns "does this deployment keep data" into a fact about the past. That is
strictly stronger than a guess and strictly weaker than a prediction, which is the correct epistemic
position and the one this project's culture demands.
</objective>
