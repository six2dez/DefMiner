# Phase 06 — UI Design Contract

> Visual and interaction contract for the Scan tab, the toolbar scan indicator, the progress
> readout, and the Settings storage statement. Generated by gsd-ui-researcher, verified by
> gsd-ui-checker.

**This document EXTENDS `05-UI-SPEC.md`; it does not replace it.** That contract was approved on
2026-08-28 with 6/6 checker dimensions PASS and Phase 5 shipped 28 frontend modules against it. Every
value in it — the stack pins, the seven-value spacing scale, the fixed 32px row, four sizes and two
weights, the mandatory `font-mono`, zero hex literals, the six Caido colour roles, R1–R5, the table
contract, the coalescing rules and the `scan_state` vocabulary — **is inherited verbatim and is not
restated here except where this phase amends it.** Where this document says nothing, the Phase 5
contract governs.

Three sections carry the deltas and nothing else:

- `## Amendments to 05-UI-SPEC.md` — the four places the upstream contract's own text must change,
  each with its reason. The planner carries these upstream; they are amendments, not divergences.
- `## New Surfaces` — the four surfaces D-13, D-14, D-19 and D-25 add.
- `## Named Conflicts` — the one place a Phase 5 rule genuinely could not accommodate a Phase 6
  surface, stated with the evidence rather than quietly worked around.

**The hardest problem in this phase is a copy problem, not a visual one.** D-14 forbids a percentage
and forbids a progress bar. A readout with no denominator has to read as *progress* rather than as a
stalled screen, on a job that can run for hours, on a backend whose single QuickJS thread genuinely
does stop moving for seconds at a time. `## The Progress Readout` is the answer and it is the longest
section here on purpose.

## Spacing Scale

**Inherited verbatim from `05-UI-SPEC.md § Spacing Scale`.** Seven values — 4 / 8 / 16 / 24 / 32 / 48
/ 64 — expressed as Tailwind v3 utilities. Restated here only as the mapping onto Phase 6's surfaces,
because the checker's Dimension 5 reads this section.

| Token | Value | Tailwind | Phase 6 usage |
|-------|-------|----------|---------------|
| xs | 4px | `-1` | Gap between a counter's label and its number in the progress strip; gap inside the toolbar indicator between its state word and its counter |
| sm | 8px | `-2` | Horizontal padding on the toolbar indicator, the scan controls and every button on the Scan tab (`px-2 py-1`, matching every shipped button); gap between the three scan controls |
| md | 16px | `-4` | Gap between the Scan tab's stacked blocks; left margin separating each toolbar element from the one before it (`ml-4`, matching the shipped Export button and pill) |
| lg | 24px | `-6` | Padding inside a Scan-tab section and inside the Settings storage section (`p-6`, matching `SettingsPanel.vue`'s shipped sections) |
| xl | 32px | `-8` | Gap between cells in the progress counter strip (`gap-8`, matching the health strip) |
| 2xl | 48px | `-12` | **The toolbar height, unchanged**, and the progress counter strip's fixed height (`h-12`, the same utility `HEALTH_STRIP_HEIGHT_CLASS` already resolves to) |
| 3xl | 64px | `-16` | Vertical breathing room around the Scan tab's empty state |

**Exceptions: none.** Every Phase 6 spacing value is one of the seven above.

**The 32px row height is untouched and unreferenced.** `TABLE_ROW_HEIGHT_PX` and its
`ROW_HEIGHT_CLASS` lookup govern the virtualised entity tables. **No Phase 6 surface is virtualised**
(see `## The Scan History List`), so no Phase 6 surface consumes the fixed row height, and nothing
here can drift it. The `xl` step is spent on the counter-strip gap instead.

**The toolbar's 48px is a hard budget and the scan indicator lives inside it.** The header is
`h-12 flex shrink-0 items-center px-4` and gains no height. The indicator uses the exact class
signature the shipped Export button and coalescing pill already use — `ml-4 border border-surface-600
px-2 py-1 text-xs font-semibold` — so it consumes `sm` padding inside a row whose height is set by the
`2xl` step and by nothing in the indicator. A Phase 6 element that needed more than one line in the
toolbar would be an element that belongs on the Scan tab.

## Typography

**Inherited verbatim from `05-UI-SPEC.md § Typography`: four sizes, two weights (400 / 600), the
per-role line heights, and the mandatory `font-mono` security control.** No new size, no new weight,
no new family. The mapping onto Phase 6's surfaces:

| Role | Size | Weight | Line Height | Phase 6 application |
|------|------|--------|-------------|---------------------|
| Label | `text-xs` / 12px | `font-semibold` (600) | `leading-normal` / 1.5 | Counter labels in the progress strip; the toolbar indicator in its entirety; every button label; the scan-history column headers; the reject-reason keys |
| Body | `text-sm` / 14px | `font-normal` (400) | `leading-normal` / 1.5 | The position line, the no-denominator note, every suspension reason, the storage statement, the footprint counts, all prose |
| Heading | `text-lg` / 18px | `font-semibold` (600) | `leading-snug` / 1.375 | The Scan tab's section titles and the Settings storage section title — the same `text-lg font-semibold leading-snug` `HealthPanel.vue` and `SettingsPanel.vue` already use |
| Display | `text-2xl` / 24px | `font-semibold` (600) | `leading-tight` / 1.25 | The Scan tab's empty-state heading only. Nothing else. |

**`font-mono` on Phase 6 surfaces — three strings carry it, and one of them is not what the security
argument was written for.**

1. **DefMiner's own asset clause**, shown as non-editable context on the start form. `font-mono`
   because HTTPQL is code: parentheses, colons and quoted literals are what the operator is checking,
   and a proportional face makes a nesting error invisible.
2. **The operator's HTTPQL clause**, in the form input, in the scan-history row and in the per-scan
   detail. Same reason — plus one that *is* the security argument: an operator composing a filter
   about a target routinely pastes a hostname **copied from the target's own page**, which can carry a
   bidi override or a C0 control. So this string is sanitised through `safety/display.ts` before it
   renders, exactly as a target-controlled string is. **State the reason precisely in the code: this
   is not a claim that the operator is hostile, it is a claim that the operator's clipboard has been
   in contact with the target.**
3. **Nothing else.** The counters are integers, the state words are DefMiner-authored, and the
   position timestamp is DefMiner-formatted. None of them is `font-mono`; applying it to a plain
   integer would dilute the signal the rule exists to carry — that mono means *this text came from
   somewhere I do not control*.

**Numbers are Body weight 400, never bold.** The shipped health strip renders its label at
`text-xs font-semibold` and its value at `text-sm` (weight 400), and the progress strip matches it
exactly. Two weights remain two.

## Color

**Inherited verbatim from `05-UI-SPEC.md § Color`: the six `@caido/tailwindcss@0.1.0` roles, zero hex
literals, `surface-400` as the neutral level-4 tone (FLAG F4, resolved in
`scan-state-presentation.ts`), and colour never as the sole carrier of meaning.**

| Role | Value | Phase 6 usage |
|------|-------|---------------|
| Dominant (60%) | `bg-surface-900` | The Scan tab body, unchanged from every other tab |
| Secondary (30%) | `surface-800` / `surface-700`, borders `surface-600` | The toolbar the indicator sits in; the progress strip's border; every Scan-tab section border; the Pause and Resume controls |
| Accent (10%) | `primary-500` | **The five reserved uses, unchanged.** Phase 6 consumes exactly two of them: the active-tab treatment when `Scan` is the active tab (use #2), and the focus ring on every interactive element it adds (use #3). **It adds none.** |
| Destructive | `danger-500` (hover `danger-400`) | **Five named elements — up from four. See the amendment below.** |

### Accent: the not-list holds, and the toolbar indicator is on it

The scan indicator is a stateful readout that is also a button. It is **not** accent-toned. The
`05-UI-SPEC.md` not-list already names "the export button" and "any state that merely means
interactive"; the indicator is both, and it is `surface`-toned with a border exactly as the shipped
Export button and coalescing pill are.

**The temptation this rule exists to refuse:** a running scan is the most interesting thing on the
page and the obvious move is to paint it the accent colour. That would make the accent mean "notice
this" instead of "this is the one confirm / the one active tab / the focus ring", and once the accent
means "notice this" nothing on the page can be quieter than anything else. The indicator earns
attention by *existing only while there is a scan*, which is a stronger signal than a hue.

### Destructive: the count moves from four to five

**"Discard scan" is the fifth destructive element**, and this is an amendment to `05-UI-SPEC.md`,
carried upstream rather than diverged from. The reasoning, since it changes a number the checker
verified:

- **It is genuinely irreversible.** D-26 makes a suspended scan's row *its cursor*. Discarding
  destroys a walked position that may represent hours of serial backfill, and the walk cannot be
  cheaply redone — that is the whole reason D-12 walks descending and D-09 persists a position at all.
- **The audit ledger already agrees.** D-16 says a scan writes to `audit` in exactly two cases, and
  discard is one of them. `audit` is the age-exempt ledger Phase 5's D-06 raised the row bound on
  specifically to preserve permanent-consequence records. If the durable ledger treats discard as
  permanent, the UI must not present it as ordinary.
- **The alternative was considered and rejected.** Expressing discard some other way — surface-toned
  with a confirmation dialog — would break the one property the destructive role has: that its uses
  are *exactly* the irreversible ones and nothing else. A sixth irreversible action rendered in
  `surface` would make the role's list a historical accident rather than a rule.

**Destructive (`danger-*`) reserved for exactly these five:**

1. The confirm button in the **Create Caido Findings** dialog (FIND-01)
2. The confirm button in the **Export with raw values** dialog (UI-06)
3. The `failed` scan-state badge, and analysis error text in the evidence panel (ERR-04)
4. The count in the partial-view banner when it includes failed artifacts (FLAG F3, resolved by P5-D67)
5. **The confirm button in the Discard scan dialog** *(new — D-10)*

**And the corollary that matters more than the addition: Pause is NOT destructive.** D-10's entire
point is that cancel means pause, so a mis-clicked cancel on a multi-hour backfill costs nothing. If
Pause and Discard sat adjacent in the same tone, the operator would hesitate over the safe one and the
asymmetry D-10 bought would be invisible. **Pause and Resume are `surface`-toned with a border, and
Discard is `danger`-toned and separated from them by the `sm` gap plus its own confirmation
ceremony.** That visible asymmetry *is* D-10, rendered.

### Semantics: the two shipped colours, and what a suspension is

| Semantic | Token | Phase 6 usage |
|----------|-------|---------------|
| `success` | `success-500` | The **Finished** scan-lifecycle state and nothing else on these surfaces |
| `info` | `info-500` | The **Suspended** state, the **Not advancing** stall marker, and the observed-restart-loss sentence in Settings |

**A suspension is `info`, not `danger`, and the reasoning is load-bearing.** Every route to
`suspended` is either operator-initiated (Pause, D-10), expected and recoverable (project epoch
change, D-04; process restart, D-11), or a resource bound doing its job (retention eviction, D-08).
**Nothing failed.** `danger` on this state would paint a red block on a correctly-functioning backfill
and would put the fifth destructive use next to a sixth non-destructive one. `info` is the same role
the shipped `partial` badge carries and means the same thing here: **stopped early — what you have is
a floor, not a total.** That is exactly what a suspended scan's counters are.

**Restart-loss in Settings is also `info`, for the same reason.** A container with no persistent
volume is not broken; it is what it is, and DefMiner is reporting an observation. Painting it `danger`
would tell an operator their tool failed when their deployment merely does not persist.

**The palette still has no `warning` role** and this phase does not invent one. Every state above
carries its word.

**Colour is never the only carrier of meaning, restated as a Phase 6 rule with teeth:** the toolbar
indicator, which is the smallest element in the phase and the one most tempting to reduce to a
coloured dot, **always renders its state word**. There is no dot-only form of it, and there is no
form of it that carries a tone class without the word in the same element — the same one-element
coupling `StatusBadge.vue` enforces, for the same reason: an implementation that put the colour on a
dot and the word somewhere optional lets a later edit drop the word and keep the dot.

## Two Vocabularies With One Name — How They Are Kept Apart

This is the highest-risk detail in the phase and it is a naming problem, not a visual one.

`scan_state` is the **analysis** state of one artifact — the shipped, database-CHECK-enforced
`pending` / `running` / `done` / `partial` / `failed`, rendered by `StatusBadge.vue` from
`SCAN_STATE_PRESENTATION`. Phase 6's `scans.state` is the **lifecycle** state of a retroactive scan —
`running` / `suspended` / `completed` / `discarded`. Two closed vocabularies, one word "scan", and
`running` is a literal member of both. An operator who reads "Running" and cannot tell whether *this
artifact's analysis* or *a retroactive backfill* is running has been told nothing.

**Five mechanisms keep them apart, in the order they act:**

**1. The column is named `state`, never `scan_state`.** `analyses.scan_state` already exists. Two
different closed vocabularies under one column name in one SQLite file is the drift shape this repo
keeps catching, and `COLUMN_ALLOWLIST` would happily accept it.

**2. The TypeScript vocabulary is `SCAN_LIFECYCLE_STATES` / `ScanLifecycleState`**, declared in
`@defminer/engine/contract` *beside* `SCAN_STATES` — one file, two adjacent declarations, so the
collision is visible at the point of declaration rather than discovered at a call site.

**3. No label is shared, and no label is a prefix of another label.**

| Vocabulary | Member | Operator-facing word |
|---|---|---|
| analysis (`scan_state`, shipped) | `pending` | **Queued** |
| analysis | `running` | **Analysing** |
| analysis | `done` | **Complete** |
| analysis | `partial` | **Partial** |
| analysis | `failed` | **Failed** |
| lifecycle (`scans.state`, new) | `running` | **Scanning** |
| lifecycle | `suspended` | **Suspended** |
| lifecycle | `completed` | **Finished** |
| lifecycle | `discarded` | **Discarded** |

**"Finished", not "Completed".** The obvious label for `completed` is "Completed", and it must not be
used: the analysis vocabulary already ships "Complete", and *Complete* / *Completed* is a
one-character difference on a triage surface where the two states mean opposite things ("every byte of
this artifact was inspected" vs. "this backfill reached the end of history"). "Finished" shares no
prefix with any shipped label and reads correctly for a job.

**4. The assertion, so this is mechanical rather than remembered.** A source-level check — in the
idiom `sanitise.spec.ts` uses to permit `forDisplayText` beside `forDisplay` — asserts that
**no label in either presentation map is a case-insensitive prefix of any label in the other.** A
plain set-disjointness check is not enough: it would pass "Complete" beside "Completed", which is the
exact pair this rule exists to catch.

**The assertion walks the COMPUTED words too, not only the map members.** Three of the four
operator-facing words for lifecycle `running` — `Starting…`, `Waiting for the analysis queue`,
`Not advancing` (`## The Progress Readout` D3) — are computed presentation states and are not members
of `SCAN_LIFECYCLE_PRESENTATION`. A guard over map members alone therefore covers only half the
strings an operator actually reads. The check takes the union of both presentation maps' labels
**and** the computed lifecycle words, and asserts the prefix rule across that union. No collision
exists today, which is precisely why the guard must be widened now rather than after one is
introduced: the whole point of mechanism 4 is that this is mechanical rather than remembered, and a
guard that covers half the surface is remembered for the other half.

**5. Separate presentation module, separate renderer, separate marker.**
`SCAN_LIFECYCLE_PRESENTATION` is its own `Record<ScanLifecycleState, …>` in its own file, with its own
component and its own `data-defminer-*` marker. It does **not** widen `StatusBadge`'s prop.
`StatusBadge.vue`'s header already records why the map is a `Record` over a closed union — a widened
prop taking a union of two vocabularies would give the compiler nothing to check and would put the
`Complete`/`Finished` decision inside a component instead of inside a type.

**And they never appear in the same row.** The analysis state appears in an entity table's leading
cell and in the evidence panel. The lifecycle state appears in the toolbar indicator and on the Scan
tab. No surface renders both.

## New Surfaces

Four, all fixed by locked decisions. This section specifies how they look and behave.

### 1. The fifth tab (D-13)

**Position: third. `Artifacts · Observations · Scan · Health · Settings`.**

The strip's two halves are entity classes then operational chrome, and `Scan` is operational: it is
the job that *fills* the two entity tables. Placing it third keeps the entity tabs contiguous and
first, keeps the operational tabs contiguous, and keeps Settings last where the convention puts it.

**The rejected alternative and its real cost.** Appending fifth would preserve every existing tab's
index, which `App.vue:63-66` argues for ("the tab an operator reaches for by muscle memory does not
move under them"). That argument is about *runtime sorting*, not about a version that visibly gains a
tab — and the cost of appending is that `Scan` would sit after `Settings`, which reads as an
afterthought for the surface D-13 exists to make visible. The muscle-memory cost is paid once, at
upgrade, and D-13's toolbar indicator means the operator does not have to *find* the tab to learn a
scan is running.

**The wrap rule holds at five and does not change.** The strip stays
`flex shrink-0 flex-wrap gap-2 border-b px-4 py-2`. Five `text-xs` labels — Artifacts, Observations,
Scan, Health, Settings — fit one row at any plausible Caido panel width and wrap to a second when they
do not. **Never a horizontal scroller and never an overflow menu**, unchanged: a hidden tab is a
surface the operator never opens, and that argument gets stronger at five, not weaker. A second row
grows the strip and the `min-h-0 flex-1` body absorbs it; the toolbar's 48px is unaffected.

**`TabId` is a closed union and `App.vue`'s body chain ends in a bare `v-else` on Health** —
deliberately, per its own comment, so a fifth tab added without a body lands somewhere visible. Adding
`scan` therefore requires adding both the `TABS` entry **and** its `v-else-if` arm, and the shipped
comment must be updated in the same commit rather than left describing a four-member union.

### 2. The toolbar scan indicator (D-13)

The toolbar's first stateful element. Nothing lives there today but the title, the Export CTA and the
transient coalescing pill.

| Property | Value |
|---|---|
| Position | **Fourth of four: `DefMiner` · `Export inventory` · **scan indicator** · coalescing pill.** Export keeps its shipped slot — it is the primary CTA and must not move when a scan starts. The pill stays last because it is the most transient. |
| Height | **None of its own.** `ml-4 border border-surface-600 px-2 py-1 text-xs font-semibold` — byte-identical to the shipped Export button's and pill's class signature. The 48px comes from the header's `h-12` and the indicator contributes nothing to it. |
| Shape | A `<button>`, `type="button"`, carrying `FOCUS_RING_CLASS`. `whitespace-pre`, never wraps, `shrink-0`. |
| Content | **State word · one counter · position date**, e.g. `Scanning · 8,412 seen · 14 Aug 2026`. Always all three; never a bare word and never a bare number. |
| Colour | The lifecycle tone class on the same element as the word (`## Color`). `surface-400` for Scanning, `info-500` for Suspended. |
| Clickable | **Yes — it switches the active tab to `Scan`.** Same mechanism as the shipped `openHealth()`: `App.vue` owns the strip and the indicator calls into it. A readout the operator cannot act on is a readout that ends the sentence one word early. |
| Animation | **None. Anywhere.** No pulse, no spinner, no transition. Motion that carries no information is the fabricated-progress shape D-14 refused, and this element may be on screen for hours. |
| Icon | **None**, per the no-icon-only rule and the absent icon library. |

**When it renders, which is the decision that matters:**

| Lifecycle state | Indicator |
|---|---|
| No scan row for this project | **Absent.** A chip reading "No scan running" is chrome that says nothing and trains the operator to stop reading the slot — `App.vue:641-643`'s own argument for the pill, applied. |
| `running` | **Present.** |
| `suspended` | **Present, and this is the load-bearing case.** Every non-operator route to `suspended` — epoch change (D-04), restart (D-11), retention eviction (D-08) — produces a scan the operator did not stop and would otherwise never learn had stopped. A suspended scan that is invisible from four of five tabs is exactly the frozen-looking page D-13 exists to prevent, one level up. |
| `completed` / `discarded` | **Absent.** A terminal scan is history; the Scan tab holds it. |

**Its bound, stated because the toolbar does not wrap.** The header is a single non-wrapping row and
every element in it is a DefMiner-authored bounded string: a fixed title, a fixed CTA label, a fixed

one grouped integer, and a fixed-width formatted date. **No target-controlled string, and no unbounded
string, may ever be added to the toolbar.** That is the rule that keeps the 48px honest, and it is
worth more than a truncation policy would be.

### 3. The Scan tab body

A single scrolling column in the `2/3` region, exactly as `HealthPanel` and `SettingsPanel` are —
`flex flex-col gap-4 overflow-y-auto`.

**The evidence panel stays mounted, and that was weighed rather than assumed.** Taking the panel's
`w-1/3` back for the Scan tab was considered and **rejected**: the panel's unconditional mount is the
shipped no-reflow guarantee (`App.vue:774-778`), conditioning it on tab identity would make its
presence a function of two things instead of one, and Health already demonstrates that an operational
surface reads fine in `2/3` with a fixed counter strip and a `<dl>` below it. An amendment to approved
layout has to buy something; this one does not. Recorded here so the planner does not rediscover it.

**Vertical order, top to bottom:**

1. **The status line and the position line** — first, because the operator's question on arrival is
   "is it moving".
2. **The progress counter strip** — four counters, fixed height, no wrap.
3. **The no-denominator note** — one line, once.
4. **The remaining counters and the reject-reason breakdown** — a `<dl>`, the shape `HealthPanel`
   already uses for its per-counter explanations.
5. **The controls** — `Pause` / `Resume` (surface) and `Discard scan` (danger), separated.
6. **The scan history list**.

**Blocks 1–5 render only when there is a `running` or `suspended` scan. When there is not, block 1's
slot holds the start form instead.** The live readout and the start form are the same question in two
states and are **never both on screen**. A disabled start form beside a running scan is chrome whose
only content is "no".

### 4. The start form (D-05)

| Field | Shape |
|---|---|
| **DefMiner's asset clause** | Read-only, `font-mono`, always visible, cannot be edited or removed. Rendered as context, not as an input. |

## The Progress Readout

**The hardest copy problem in the phase.** D-14 gives absolute counters and a position timestamp, no
percentage, no denominator and no bar — because Caido offers no cheap count for an HTTPQL filter, a
counting pass would cost the same full body transfer the scan itself does, and a percentage against an
operator-supplied guess is the fabricated-number shape Phase 0 refused. The problem this section
solves: **a readout with no fraction must read as progress rather than as a stalled screen**, on a job
that runs for hours, on a backend whose single thread genuinely does stop for seconds at a time.

Five devices, in the order they carry weight.

### D1 — Movement is the evidence, so the fastest-moving counters lead

Progress with no denominator is demonstrated by **change over time**, so the surface is built around
what changes. The counter strip carries the four that move, in this order:

| Cell | Moves | Why it is in the strip |
|---|---|---|
| **Requests seen** | every page, +20 | The fastest-moving number and the one that most directly means "the walk is walking" |
| **Admitted** | every page | Progress toward the thing the operator actually wants |
| **Queued** | every admission | Reveals the backlog between the scan and the analysis |
| **Analysed** | every completed analysis | The other end of the pipe; the gap to Queued is the backlog, made visible without arithmetic |

`Pages walked`, `Skipped (already analysed)` and `Rejected` sit in the `<dl>` below the strip with
their per-counter explanation, exactly as `HEALTH_COUNTERS`' `help` text does. **Four in the strip and
not seven** for a shipped reason: `health-contract.ts:177-189` fixes the strip's height at `h-12` with
`whitespace-pre overflow-hidden` cells and no `flex-wrap`, because a strip whose height is decided by
its content is a strip that grows the first time a counter passes a million. Seven cells at `gap-8`
would wrap at plausible widths, and a wrapping strip reflows what is below it.

**Every counter is grouped by `groupThousands` from `table-contract.ts`.** Never `toLocaleString`,
never a second grouping helper — that argument is already written twice in the shipped source.

### D2 — The position line is the narrative a counter cannot be

**`Now scanning traffic from 14 Aug 2026, 09:41`.**

Because D-12 walks descending, this date **marches backwards into history**, and a date moving
backwards is legible as progress in a way a rising integer is not: it answers "how far back have I
got", which is the question the missing denominator was going to answer.

| Rule | Value |
|---|---|
| Source | **`item.request.getCreatedAt()`, never the stored `observed_at`.** `consumer.ts:528` stamps every persisted row with `Date.now()`, so a response captured on 14 August is *stored* with today's date. A position line built from the stored row would read "now scanning traffic from today" for the entire walk — the single most misleading string this surface could produce. |
| Format | DefMiner-authored, from a frozen 12-entry month table. **Never `toLocaleString`** — same argument `groupThousands` already makes: it reads differently under a different locale and these strings are compared literally by specs. |
| Precision | **Date and time to the minute on the Scan tab; date only in the toolbar indicator.** A scan covering a single day would leave a date-only line frozen while the counters moved, which is the appearance this whole section exists to prevent. The toolbar is a bounded slot and the tab is the detail surface. |
| Zone | Local. The operator's mental model of "when was I browsing" is their own clock, and the label says "traffic from", not a timestamp field. |
| Before the first page resolves | **Absent, never a placeholder date and never the epoch.** The status line carries "Starting…" instead. A number DefMiner does not have is absent, never zero — `App.vue`'s own rule for a still-resolving tab count. |

**And an honesty note that belongs in the code:** the position line is *not* the primary movement
signal, precisely because of the single-day case. D3's stall marker is derived from **any counter
moving**, never from the date advancing.

### D3 — Three words for "not moving", because only one of them is bad

A single "Running" label would make three very different situations look identical. The status line is
a computed **presentation** state — distinct from the four persisted lifecycle states — over this set:

| Status line | Condition | What the operator should conclude |
|---|---|---|
| **Starting…** | `running`, no page has resolved yet | Nothing is wrong; the first query is in flight |
| **Scanning** | `running`, a counter moved within the threshold | It is working |
| **Waiting for the analysis queue** | `running`, held at D-01's backpressure watermark | **It is working correctly and deliberately paused.** The scan pages only while queue depth is below the watermark so live browsing always wins. Without this word the operator reads a legitimate backpressure hold as a stall. |
| **Not advancing** | `running`, no counter has moved for longer than the threshold, and not at the watermark | Something is wrong, or one very large artifact is being walked. Routes to Health. |
| **Suspended** | `suspended` | Stopped, with a reason, resumable |
| **Finished** | `completed` | Reached the end of the filter's range |
| **Discarded** | `discarded` | History only |

**The stall threshold is `ARTIFACT_DEADLINE_MS` (30,000), imported and never restated.** Derived, not
chosen: at `TOKENIZER_MS_PER_MB = 783` a full `PASSIVE_MAX_BYTES` (8 MiB) artifact takes ~6.3 s to
walk on a strictly serial thread, and `ARTIFACT_DEADLINE_MS` is the shipped ceiling on any single
artifact. A threshold below it would cry wolf on every large bundle. State the derivation where the
constant is used, in the `POLICY_DERIVED_FROM` idiom.

**"Not advancing" is `info`, not `danger`, and it names the cause it cannot see.** It is the same
UI-09 move the `partial` badge makes: a state that is not "complete" is marked in words rather than
silently presented as fine. Its copy routes to Health by name, exactly as the shipped inventory-table
error copy does — because a blocked QuickJS thread is precisely what Health's four counters exist to
distinguish from a stuck interface (`PITFALLS.md` P3).

### D4 — The absent denominator is stated once, as a decision

**One line, directly under the strip, never repeated per counter:**

> **There is no percentage.** Caido cannot count the requests matching a filter without transferring
> every response body — which is the scan itself. A total would cost a second full pass, so DefMiner
> reports what it has done rather than guessing what is left.

Without this the operator reads an omission and infers a bug. With it, the missing fraction is a
stated engineering position they can agree or disagree with. **This is the single most important
sentence on the surface.**

It is rendered as prose in Body weight, not as a tooltip and not behind a disclosure. R2 bans
target-controlled content in tooltips; this string is DefMiner's own, so the ban does not reach it —
but a sentence that explains why the surface looks the way it looks must not be hidden behind an
interaction the operator has no reason to perform.

### D5 — Nothing on this surface is indeterminate

No progress bar (`progressbar` is available and banned), no spinner (`progressspinner` likewise), no
pulse, no animated ellipsis, no shimmer. **The only things that move are numbers that mean something.**

The reasoning generalises the shipped no-centred-spinner rule and adds a second, independent leg: a
spinner claims "something is happening" while refusing to say what, and D-14's whole subject is
refusing to claim more than is known. A tool that will not fabricate a percentage must not fabricate
reassurance either.

**The in-flight label convention still applies to the controls.** `Pause` becomes `Pausing…`,
`Resume` becomes `Resuming…`, disabled while in flight — its own label, not a spinner beside the old
one, the rule the shipped Save and Refresh actions already obey.

## Data & Interaction Contract

### Event coalescing — D-15, settled here so the planner is not choosing

**`06-RESEARCH.md` offers two shapes. This contract fixes shape (b): scan progress rides
`INVALIDATION_EVENT` as a distinct payload variant, routed to its own small throttled store, outside
`INVALIDATION_CATEGORIES`, outside `pending`, and outside the coalescer entirely.**

| Property | Value |
|---|---|
| Channel | The **existing** `INVALIDATION_EVENT`. D-15's "one backend→frontend mechanism" is honoured. |
| Category | **Not a fourth `InvalidationCategory`.** `INVALIDATION_CATEGORIES` stays at three, and `contract.spec.ts`'s `toEqual([...]).toHaveLength(3)` stays green untouched. |
| Routing | The frontend discriminates the payload **before** `coalescer.onSummary` sees it. A progress payload never enters `pending`. |
| Throttle | **Leading + throttled at `MAX_REACTIONS_PER_SECOND` (2/s), imported from `coalescer.ts` and never restated. No trailing debounce.** |
| Triage lock | **Not read.** Neither `triageLocked` early-return is modified, reached, or duplicated. |
| Side effects | The progress store **never** calls `refresh()` and **never** refetches an entity table. |
| The pill | Scan progress **never** increments `pendingTotal` and never changes the pill's label. The pill belongs to the entity tables. |

**Why (b) and not (a).** Shape (a) — teaching both `triageLocked` guards "…unless every pending
category is scan progress" — puts a conditional into the one file whose value is that it has none, and
requires editing `INVALIDATION_CATEGORIES`, the gate P5-D18 added specifically to stop speculative
categories arriving through the back door. Shape (b) leaves the triage-lock invariant *literally
unmodified*. That invariant protects durable triage state from a mis-click; it is not something to
route a progress strip through and then carve an exception out of. **A progress strip has no rows and
no cursor, so the correct relationship to the triage lock is not "exempt from it" but "never behind
it".**

**Why leading-throttled and not trailing-debounced, which is a real behavioural difference and must be
stated rather than inherited by accident.** P5-D60 measured what a pure trailing debounce does to a
sustained stream: **zero reactions over three simulated seconds of 20 events/second**, because the
window never elapses while events keep arriving. The entity coalescer solves that with a `maxWait`.
For a progress readout the right answer is simpler and different: the **first** update must land
immediately — an operator who has just pressed **Start scan** and watches an unchanged screen for
500 ms has already learned the wrong thing — and the rest are capped. So: **the entity coalescer
debounces trailing with a `maxWait`; the progress store throttles leading.** Two different mechanisms
because they answer two different questions, stated here so the difference is a decision rather than a
divergence.

**Three assertions this contract asks for**, because each is a rule that decays silently:

1. A spec that **selects a row**, emits a progress payload, and asserts the readout advanced —
   proving the triage lock is not in the path.
2. A spec that emits 20 progress payloads in one simulated second and asserts **2** reactions —
   the cap, proven the way `coalescer.spec.ts` already proves its own.
3. A spec asserting a progress payload leaves `pendingTotal` at zero and the pill unrendered.

**The payload amendment, stated rather than exceeded.** `05-UI-SPEC.md` says verbatim: *"Backend→
frontend events carry an invalidation summary only: `{ projectId, category, changedCount, newestId }`.
No findings payload, no bundle bodies."* The progress variant carries **DefMiner-authored integers and
one DefMiner-formatted timestamp derived from `getCreatedAt()`** — no target-controlled bytes, no
bodies, nothing the operator's screen has not already been shown. The *spirit* of the rule holds
exactly; the *shape* changes, and `05-UI-SPEC.md` is amended for it (`## Amendments`) rather than
quietly exceeded.

### The scan history list — it does NOT reuse the shipped table contract

**And the deciding fact is mechanical, not aesthetic: `assertColumnContract` throws on a table with no
target-controlled column.** It requires *exactly one*
(`table-contract.ts`: `if (targetControlled.length !== 1) throw`). Every column of the scan history —
lifecycle state, counters, position date, and the operator's own HTTPQL clause — is DefMiner-authored
or operator-authored. **Zero are target-controlled.** The shipped contract is literally incapable of
expressing this table, and forcing a column to claim `targetControlled: true` to satisfy the assertion
would be lying to a gate.

The rest of the contract does not fit either, for reasons that all point the same way:

| Shipped table rule | Why it does not reach the scan history |
|---|---|
| 100-row keyset pages, cursor never `OFFSET` | The set is bounded by construction: one scan at a time, rows aged out by normal retention, growth bounded by the row cap. Realistically tens of rows. A keyset endpoint for a set that fits in one read is cost with no benefit. |
| `RecycleScroller` at fixed `item-size: 32` | A virtualised scroller over ~12 rows. And the per-scan detail is an **inline disclosure under the selected row**, which is a variable row height — the one thing `RecycleScroller`'s fast path forbids. |
| 2,000-row in-memory window | Nothing to bound. |
| Server-side sort and filter, client sorting banned | That ban exists because sorting a 2,000-row window would sort a *subset* and present it as the whole set. Here the resident set **is** the whole set, so the defect it prevents cannot occur. **The list is nonetheless not sortable at all** — it renders newest-first, always, because a scan history's only meaningful order is chronological and a sort control would be a control with nothing to buy. |

**What it does inherit, and this is not optional:** `FOCUS_RING_CLASS`; `groupThousands` and `counted`
for every number and every singular/plural agreement; the no-icon rule; `font-mono` plus sanitisation
on the operator's clause; and the shipped state discipline — skeleton rows rather than a spinner while
loading, and **an explicit error rather than an empty list** on a failed load. That last one carries
the suppressions-list argument verbatim: an empty scan history means "you have never run a scan", and
rendering a load failure that way tells the operator the opposite of the truth — while a suspended
scan they cannot see is a resumable cursor they will never resume.

**Its bound, stated rather than omitted** (the shape P5-D20 established for the suppressions list):
**the 50 most recent scans, newest first, with every `suspended` scan pinned in regardless of age.**
When the list is capped it says so. The pinning is the load-bearing half — a suspended scan's row *is*
its cursor (D-26 exempts it from the age bound for exactly that reason), and hiding one below a
display cap would hide an operator's unfinished work behind a number nobody chose deliberately.
**50 is a defensible proposal, not a measurement**; what should survive if the number moves is the
shape of the answer — a stated bound, with suspended rows exempt from it, enforced at read.

### The scan status payload — required fields

**This is a binding contract on the backend's status shape, not a frontend preference.** It is
restated here, in the contract section, because `## Open Decisions` opens by saying every `U6-` row
"ships under the stated default; none blocks planning" — and U6-6 is the one row that is not a
default. A planner who reads that preamble first would take the held-at-watermark signal as optional,
and the consequence is not cosmetic.

The scan status the frontend reads MUST carry an explicit **held-at-watermark** signal — a boolean
(or an equivalent named reason) stating that the producer is currently withholding pages because
queue depth is at or above D-01's watermark.

**Why it cannot be derived, and what breaks without it.** From outside the backend, a scan holding at
the watermark and a scan whose QuickJS thread is blocked are indistinguishable: both show counters
that stop advancing. `## The Progress Readout` D3 spends three words on "not moving" precisely
because only one of them is bad — `Waiting for the analysis queue` is the healthy backpressure hold
that D-01 designs for, and `Not advancing` is the stall marker that fires at `ARTIFACT_DEADLINE_MS`.
If the signal is absent, `Waiting for the analysis queue` can never render, every legitimate
watermark hold falls through to `Not advancing`, and the stall marker cries wolf on the single most
common healthy state of a long backfill. An operator who learns to ignore a stall marker is worse off
than one who never had it — the same argument `PROJECT.md` § Core Value makes about false positives.

U6-6 in `## Open Decisions` is a pointer to this line, not an independent decision.

## Named Conflicts

One. It is stated here rather than worked around silently, per the brief.

**The coalescer's triage lock cannot serve a progress readout, and D-15's word "category" cannot be
taken literally.**

- **The Phase 5 rule:** *"While the operator has a row selected or the evidence panel open, the table
  does not re-order or re-render rows. New counts accrue into the coalescing pill and apply on
  Refresh."* Implemented as two `triageLocked` early-returns at `coalescer.ts:166` and `:206`, the
  second checked **before** the debounce window so a locked summary never enters it at all.
- **D-15:** progress rides the coalescer *as a new category*, and *"the never-re-order-while-a-row-is-
  selected rule does NOT apply to a progress strip, so scan updates land immediately rather than
  accruing into the pill."*
- **The conflict:** a `scans` category added literally would be counted into `pending` and never
  applied while a row is selected — the exact opposite of D-15's stated intent. The two are not
  reconcilable as written.
- **The resolution, and it satisfies both:** progress rides the **same event** (D-15's actual reason —
  one backend→frontend mechanism) but is **not an `InvalidationCategory`** (D-15's mechanism, which
  cannot deliver its own intent). Fixed above as the interaction contract. **The triage-lock invariant
  is not modified, not weakened and not conditionalised** — which is the outcome D-15 wanted and the
  one that keeps a mis-click from writing the wrong durable triage state.
- **What the planner owes:** the divergence from D-15's word "category" is stated in the plan, in
  those terms, rather than smuggled. The decision itself is not re-opened.

**Two things that looked like conflicts and are not**, recorded so they are not re-litigated:

- *The destructive count.* Five instead of four is an **extension** of a list the contract always
  described as growing by explicit addition, not a violation of the reservation rule. The rule is "the
  list is exact and named", and it still is.
- *The scan history not using the table contract.* The shipped contract scopes itself to the entity
  tables in every clause; `assertColumnContract` proves it mechanically by refusing a table with no
  target-controlled column. Not applying it here is obeying it, not diverging from it.
