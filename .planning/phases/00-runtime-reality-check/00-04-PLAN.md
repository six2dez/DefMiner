**Every instance in this plan is fresh and is destroyed after use. No exceptions.** The rule that must survive into every step: never run a destructive spike on an instance a later step still needs. The failure mode is not a lost instance — it is a silently wrong measurement taken on a poisoned runtime.

**Three rules that hold for every task here:**
1. **The binary.** `/Applications/Caido.app/Contents/Resources/bin/caido-cli` only, with the 0.57.1 assertion in `instance.sh` intact. Bare `caido-cli` on `PATH` is a stale 0.55.3, and a cliff measured on it would not be a reproduction of `#2211` at all.
2. **Isolation.** Every instance is launched by `scripts/spike/instance.sh` with `--data-path`. Never `--safe`.
3. **Teardown.** `kill -9`, always. `SIGTERM` on a wedged instance waits on the QuickJS thread and never returns.

**Ports owned by this plan:** 8981 through 8985. Plans 00-02 and 00-03 have finished; the long-lived recorder on 8998 is still running and is read, not disturbed, until task 3.

**Recovery is not available here.** Hot reload, `togglePlugin`, and `installPluginPackage(force: true)` all block behind the QuickJS thread — measured, with a 25-second host-log timeline. Do not write a retry loop against any plugin-lifecycle operation as a recovery path. The only recovery from a hang is killing the process.

**Requirement ID discipline.** `.planning/REQUIREMENTS.md` is the sole authority for SPIKE-nn. SPIKE-01 and SPIKE-04 happen to mean the same thing in `.planning/research/PITFALLS.md`, but five of the twelve IDs in that document collide with a different meaning, so mine its methods and never its numbers. **First, close out SPIKE-10.** It asks in words: *what is the content-hash cache hit rate on real browsing?* It is the single biggest performance lever in the project — at 40% instead of 90%, the CPU cost is six times the budget. The recorder has been accumulating since wave 1 precisely because this number is wall-clock-bound and cannot be produced on demand.

Run one final `scripts/spike/recorder-session.sh`, then `scripts/spike/cache-rate.py` to compute all three rates offline from `cache_log`: within-page-load, within-session, and across-day. Report all three, because they answer different questions, and make clear which one drives the CPU budget — the across-day rate, which is the only one a single burst can never produce. Record the number of distinct calendar days sampled and the day-over-day change in the cross-day figure.

**Set the confidence from the data, not from your own sense of the number.** Two facts pick the outcome: `CACHE_SAMPLE_DAYS`, and the `cross_day_denominator` that `cache-rate.py` emits — the count of distinct content hashes seen on two or more distinct days. A rate whose denominator is zero is **undefined, not zero**; reporting `0.0` there would tell Phase 1's CORE-08 that caching measurably never works, which is a fabrication in the opposite direction from over-reporting and mis-sizes the budget just as badly. Follow this rule literally; do not re-derive it.

- **`CACHE_SAMPLE_DAYS` is 3 or more and `cross_day_denominator` is above zero.** Set CACHE_HIT_RATE_CROSS_DAY to the measured value. Confidence is HIGH when the day-over-day change has fallen below a tolerance you state in the rationale, MEDIUM otherwise. Uninstall the LaunchAgent with `scripts/spike/recorder-agent.sh uninstall`, tear the recorder instance down preserving its data path, and record where the database was left.
- **`CACHE_SAMPLE_DAYS` is exactly 2 and `cross_day_denominator` is above zero.** Set the measured value with confidence LOW, set a `revisit_after` date, add an `unresolved` entry naming it, and leave the LaunchAgent installed so collection continues into Phase 1.
- **`CACHE_SAMPLE_DAYS` is fewer than 2, *or* `cross_day_denominator` is zero.** Either way there is no cross-day rate to report, and CACHE_HIT_RATE_CROSS_DAY carries `value: null` with `status: "inconclusive"`, a **mandatory** `revisit_after` date, and an `unresolved` entry. The exit gate permits exactly this one shape and nothing else; every other threshold in the phase keeps the non-null, non-PENDING requirement.

  **Name which of the two causes applies, in the threshold's `rationale`.** "Fewer than two distinct days sampled" and "two or more days sampled but no content hash recurred across them" are different findings implying different follow-ups — the first says keep collecting, the second says the corpus or the site list is not exercising re-serving and the method itself needs revisiting. A later reader must be able to tell them apart without re-deriving it from the raw log. Emit `CACHE_CROSS_DAY_DENOMINATOR` as a threshold in its own right so the distinction survives into the aggregate.

**When the outcome is inconclusive, additionally emit `CACHE_HIT_RATE_ASSUMED` with value `0.40` and confidence `pessimistic-default`,** with a rationale stating that Phase 1's CORE-08 cache design must budget for the worst case until the real number lands. This is what keeps Phase 1 unblocked without letting it build on a figure nobody measured.

The reasoning behind all of this is worth stating in the result's `notes`, because it is the phase's entire thesis in miniature: the job here is to replace assumptions with measurements. A measurement that could not be taken is honest output. Emitting the within-session rate under the cross-day name would be a fabrication, and it would mis-size the CPU budget by exactly the factor — 90% against 40% — that this spike exists to prevent, across eleven downstream phases. Never leave the threshold PENDING either; PENDING fails the gate and communicates nothing about why.
