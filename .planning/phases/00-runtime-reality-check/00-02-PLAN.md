<objective>
Fix every size ceiling and persistence contract the rest of DefMiner will be built against — measured inside Caido on 0.57.1, not extrapolated from bare quickjs-ng.

Purpose: four of the project's carried risks are ceilings nobody has measured. Phase 1's admission filter needs a defined length quantity to gate on. Phase 3's engine and Phase 9's parser need an AST byte threshold and a nesting depth that reflect the real 512 KiB stack under the real parser. Phase 1's storage layer needs to know whether it can rely on a PRAGMA or a transaction at all. Phase 7's sourcemap writer needs a containment strategy that works without `realpath` and without `lstat`, because JSMiner's canonical-path defence cannot be ported.

Output: `results/SPIKE-08.json`, `results/SPIKE-06.json`, `results/SPIKE-09.json`, `results/SPIKE-12.json`, and the Tier-1 build pipeline that Phase 1's DIST-05 gate will later depend on.
</objective>

  <name>Task 3: SPIKE-09 SQLite contracts, then SPIKE-12 filesystem containment on a fresh instance</name>
  <files>probe/tier0-budgets/backend/script.js, .planning/phases/00-runtime-reality-check/results/SPIKE-09.json, .planning/phases/00-runtime-reality-check/results/SPIKE-12.json</files>

Two independent questions sharing one Tier-0 probe. SPIKE-09 runs first on the shared instance; SPIKE-12 runs last on its own fresh instance because it deliberately attempts to write outside its sandbox.

**SPIKE-09 asks in words:** *do `PRAGMA` settings and `BEGIN`/`COMMIT` survive across separate `exec` calls on the pooled SQLite connection?* The plugin database is a connection pool with no transaction API and no migration framework, so if a `BEGIN` in one `exec` does not reach the `COMMIT` in the next, every multi-statement invariant in Phase 1's storage layer is unsound and STORE-01 through STORE-07 must be designed around single-statement idempotent upserts instead.

Extend `probe/tier0-budgets/backend/script.js` with functions that answer it directly. Set a `PRAGMA` in one `exec` and read it back in a separate `exec`. Issue `BEGIN` in one `exec`, an insert in a second, and `COMMIT` in a third, then read the table from a fourth and report what survived. Put a multi-statement batch — begin, several inserts, a statement that will fail, commit — into a **single** `exec` string and inspect the resulting row count to determine whether one `exec` is atomic. Read back `journal_mode` to determine whether WAL is on. Interleave a write and a read across two rapid calls to observe the pool's concurrency behaviour. Use positional `?` parameters throughout; named parameters are unsupported.

Then answer the research's open question 2, which is nearly free here and is a direct precondition for UPGRADE-01 and UPGRADE-04: *does `sdk.meta.db()` survive a plugin reinstall?* The plugin's database lives at `<data-path>/plugins/<uuid>/data.db`, and the UUID was verified stable across five `force: true` reinstalls. What is unknown is whether a genuine uninstall followed by a fresh install allocates a new UUID and therefore a new, empty database. Write a sentinel row, uninstall the package outright, reinstall it, and report whether the row is still there and whether the UUID changed. Record it as DB_SURVIVES_REINSTALL.

Write `results/SPIKE-09.json` setting PRAGMA_PERSISTS_ACROSS_EXEC, TRANSACTION_PERSISTS_ACROSS_EXEC, MULTISTATEMENT_EXEC_ATOMIC, WAL_ENABLED and DB_SURVIVES_REINSTALL, with `requirements_affected` covering SPIKE-09, STORE-01, STORE-02, STORE-05, STORE-07, UPGRADE-01 and UPGRADE-04. State in `if_wrong` what Phase 1's storage design becomes if transactions do not survive.

**SPIKE-12 asks in words:** *how does `llrt/fs` behave for containment when there is no `realpath` and no `lstat`?* JSMiner's canonical-path defence cannot be ported, and MAP-04 has to write attacker-controlled `sources` entries to disk safely without it. This is untrusted-code execution against the host filesystem, so it runs last, alone, on a fresh instance on port 8993 with a scratch data path, and nothing else is scheduled to use that instance afterwards.

Add probe functions that first **enumerate** the actual export surface of the filesystem and path modules rather than testing a hardcoded list — the type package under-declares the runtime by roughly a factor of thirteen, so enumeration is the only source of ground truth. Report whether `realpath`, `lstat`, `readlink`, `stat` and `symlink` are present. Then run the malicious-`sources` fixture set against the resolution and write path: relative traversal, absolute POSIX paths, Windows drive letters, UNC prefixes, Windows reserved device names, `webpack://` and other protocol-shaped prefixes, embedded null bytes, and Unicode forms that normalise differently. For each, record what `path.resolve` and `path.normalize` produced and where a write would have landed. Determine and record whether any symlink can be detected at all without `lstat`.

Every write attempt targets a scratch directory inside the disposable instance's own data path. Before teardown, prove containment held: snapshot the filesystem outside the scratch directory before the run, compare after, and record the result in the JSON. If anything landed outside, that is a finding of the first order and the result's `status` is `fail` with the escape path named.

Write `results/SPIKE-12.json` setting FS_HAS_REALPATH, FS_HAS_LSTAT and FS_CONTAINMENT_STRATEGY, the last stating the strategy MAP-04 must adopt given what is actually available. Record the `path.resolve` and `path.normalize` behaviour per fixture as measurements rather than thresholds. Set `requirements_affected` to SPIKE-12, MAP-04, MAP-05 and DEPLOY-04. Note that this ran on macOS only and that MAP-05's fixture suite must repeat it on Linux and Windows in Phase 7 — record it in `unresolved`-style notes rather than claiming cross-platform coverage.
