<objective>
Settle what Caido actually delivers to `onInterceptResponse`, from which surfaces, under which flags, and what it does when the plugin cannot keep up.

Purpose: three separate designs hang on these answers. ACTIVE-06's self-suppression and the `.map` probing loop depend on whether `sdk.requests.send()` re-fires the hook. FIND-03's retroactive scan is either a convenience or a correctness requirement depending on whether cached responses and 304s reach the plugin at all. CORE-03's bounded queue is sized entirely differently depending on whether Caido already queues, drops, or applies backpressure upstream of it.

SPIKE-05 and SPIKE-11 deliberately share one apparatus — a caching-aware origin plus an event log — because building it twice is the specific defect the research identified in the original phase sketch.

Output: `results/SPIKE-05.json`, `results/SPIKE-11.json`, `results/SPIKE-03.json`.
</objective>

SPIKE-11 asks in words: *do 304s and browser-cached responses reach `onInterceptResponse` at all?* The answer decides whether FIND-03's retroactive scan of already-captured traffic is a convenience feature or a correctness requirement. If a returning visitor's bundles never reach the hook because the browser served them from its own cache, then passive-only analysis has a permanent blind spot on exactly the traffic an operator generates most — repeat visits to a target.

This must be driven by a real browser, not by hand-built conditional requests. A 304 is the tail end of a *cache decision*, and `curl` with a manually supplied `If-None-Match` produces a 304 response without producing the decision path the spike is about. Use the Playwright Chromium installed by plan 00-01.

Write `scripts/spike/cache-browse.mjs` driving Chromium through the disposable instance's proxy, with the instance CA loaded so HTTPS works, against `scripts/spike/origin.py` on port 8083 serving corpus files with strong `ETag`, `Last-Modified` and a configurable `Cache-Control`. Run four scenarios, each with its own correlation marker and each followed by a drain of the event probe's log:

1. **Cold load.** Empty browser profile, first fetch. Control case — the hook must fire.
2. **Reload with a still-fresh `Cache-Control: max-age`.** The browser should serve from its own cache without touching the network at all. This is the sharpest case: if no request leaves the browser, the proxy never sees it and the hook cannot fire regardless of what Caido does. Record whether any network request was observed at the proxy at all, using Playwright's own request events as the independent witness.
3. **Reload with `Cache-Control: no-cache` and a valid validator.** The browser must revalidate, the origin returns 304, and the question is whether that 304 — which carries no body — reaches the hook, and if so what `Body.length` and `toRaw().length` report for it.
4. **Hard reload.** Cache bypassed, full 200 with body. Confirms the apparatus still delivers after the other three.

Reuse the same `probe/tier0-events` plugin from task 1 without modifying it; install it on a fresh instance on port 8996. For each scenario record: whether Playwright saw a network request, whether the proxy logged a transaction, whether the hook fired, the delivered status, and the delivered body length.

  <name>Task 3: SPIKE-03 — what Caido does with events the plugin cannot consume fast enough</name>
  <files>probe/tier0-events/backend/script.js, scripts/spike/block-load.sh, .planning/phases/00-runtime-reality-check/results/SPIKE-03.json</files>
  <action>
Run this last. It deliberately wedges the plugin thread for about thirty seconds. The research measured that during a thread block the Caido core stays healthy — GraphQL answered in 7 ms and the proxy returned 200s — and that plugin RPC is queued rather than dropped and served after the block ends, so the drain call will succeed once the handler returns. Nothing else may be scheduled behind this on the same instance.

SPIKE-03 asks in words: *what does Caido do with `onInterceptResponse` events the plugin cannot consume fast enough — queue them unboundedly, drop them, or apply backpressure?* CORE-03's bounded queue is sized completely differently under each answer, and if Caido drops silently then the plugin's own overflow counter is measuring the wrong thing.

Extend `probe/tier0-events/backend/script.js` with a blocking mode: when armed, the handler spins synchronously for a configured duration on the first delivered event and then returns, while every subsequent delivered event is still appended to the log with its sequence number and both clocks. Arm it for thirty seconds. Add two error-injection modes as well, because ERR-03 rests on the answer and this is the same apparatus: one that throws synchronously inside the handler, and one that returns a rejected promise. It is not established that Caido surfaces either.

Write `scripts/spike/block-load.sh`: arm the blocking handler, then drive exactly 500 requests through the proxy at 20-way concurrency against `scripts/spike/origin.py` on 8083, capturing per-request client-observed latency and HTTP status with `curl -w`. The research validated this exact rig at 710 requests per second with all 500 delivered to an idle handler, so the delta against that baseline is the measurement. After the block releases, drain the event log and count what actually arrived. Compare three numbers: 500 requests issued, N responses returned to the client, and M events delivered to the handler. Queue, drop and backpressure each produce a different signature — M equal to 500 with events arriving in a burst after the block is queueing; M materially below 500 is dropping; client latency inflating in step with the block is backpressure.

Report the client latency distribution explicitly, because it separates two things that are easy to conflate: a stalled *plugin thread* and a stalled *proxy*. The research asserts the proxy keeps serving during a plugin hang; confirm or correct that here with numbers.

Then run the two error-injection modes with a handful of requests each, and inspect all three log surfaces for any trace of the error: the instance's `logging.<date>.log`, its stdout, and its stderr. Record whether Caido surfaced the throw, the rejection, both, or neither, and whether the plugin kept receiving events afterwards.

Launch on port 8995 on a fresh instance for this task. Write `results/SPIKE-03.json` setting EVENT_OVERFLOW_BEHAVIOUR, EVENTS_DELIVERED_UNDER_BLOCK and HANDLER_ERROR_SURFACED, with the latency distribution and the three counts as measurements. Set `requirements_affected` to SPIKE-03, CORE-01, CORE-03, CORE-04, CORE-10, ERR-03 and OBS-01. In `verdict.if_wrong`, state what CORE-03's bounded queue must become under each of the three possible behaviours.
