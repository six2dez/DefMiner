<objective>
Decide, and then act on, what happens to the observation rows that were already written with verbatim
query strings before plan 01-07 changed the write path.

Plan 01-07 stops the bleeding. It does not clean the wound: redacting new writes does not retroactively
touch a single existing row, and those rows sit in a database `db.ts` documents as never
garbage-collected, surviving project deletion and surviving force-reinstall. Under STORE-06's bound
they persist for 90 days.

Purpose: this is the genuinely one-way part of gap 1. Rewriting or deleting those values destroys them
with no second copy, and "leave them" is also a decision — it just looks like an omission if nobody
writes it down. The operator's UAT decision was scoped to the write path ("redact at write… before the
row is written"); it did not cover rows already on disk, and this plan is where that gets settled
rather than inherited.

Output: a committed measurement of how many rows are actually affected, an operator decision taken
against that number, and — if a sweep is chosen — a convergent, scheduled, counter-visible sweep.

**Why this is a separate plan from 01-07.** 01-07 has no one-way component and no decision to wait on;
it should land, be verified and be committed on its own. Coupling it to a blocking human decision would
hold a finished security fix hostage to a conversation. Splitting also means the answer here can be
"leave them" without a half-built sweep sitting in the tree.

**Why there is no leading `type="tracer"` task.** This plan's first task is a measurement of existing
state and its second is a decision. There is no new path through the stack to prove; a tracer here
would be ceremony. `TRACER_MODE` is on, and this is the stated exception.
</objective>

<task type="checkpoint:decision" gate="blocking-human">
  <name>Task 2: Decide the disposition of pre-policy observation rows</name>
  <decision>What happens to observation rows already written with verbatim query strings</decision>
  <context>
    Plan 01-07 redacts query values at the write path. It changes nothing about rows already on disk.
    Task 1 has just measured how many of those exist — present that number from
    `results/observation-url-exposure.json` first, per database and in total, before presenting the
    options. The decision is different at zero rows than at ten thousand and the operator should not
    have to ask.

    Three properties make this worth a decision rather than a default: the database is never
    garbage-collected by Caido, it survives project deletion, and it survives force-reinstall. Under
    STORE-06 those rows persist for 90 days. And every option below except the last DESTROYS the
    values with no second copy anywhere — there is no undo, no backup, and no way to reconstruct them.

    Two further constraints the operator should have in hand: any sweep is necessarily PER PROJECT,
    because `sql-discipline.spec.ts` rejects a multi-row statement that does not scope on
    `project_id` and that rule is correct — so rows belonging to a project never reopened are not
    reached by options a or b and age out under retention regardless. And a sweep runs on the
    consumer's existing retention cadence, meaning it takes effect the next time the plugin is
    running and processing traffic, not at the moment of the decision.

    `gate="blocking-human"` is set deliberately. This project runs `mode: yolo` with
    `auto_advance: true`, and auto-mode auto-selects the first option of an ordinary blocking
    decision. Auto-selecting an irreversible deletion of the operator's own data is precisely what
    this checkpoint exists to prevent, so it stops for a human in every mode.
  </context>
  <options>
    <option id="redact-in-place">
      <name>Rewrite the existing rows through the same redactor (RECOMMENDED)</name>
      <pros>
        Destroys exactly what the operator said must not be retained — the values — and keeps exactly
        what they said must be kept: the path, the parameter names and their order. It is the same
        policy as the write path, applied backwards, so the column ends up in one consistent state
        rather than two. The artifact-to-request edge survives, so "where was this bundle seen" still
        answers for historical sightings. Convergent and cheap: one `UPDATE` per affected row, keyed
        on the full primary key.
      </pros>
      <cons>
        ONE-WAY. The values are gone the moment the sweep runs. Costs the most code of the three
        options: two SQL constants, a sweep function, a call site, a counter and a drift assertion.
        Reaches only projects the operator actually opens while the plugin runs.
      </cons>
    </option>
    <option id="purge">
      <name>Delete the pre-policy observation rows outright</name>
      <pros>
        Simplest possible implementation — a single scoped `DELETE`, self-terminating with no cursor,
        no marker and no risk of leaving a half-redacted row. Removes the exposure most completely,
        including the path, which can itself be sensitive on an internal host.
      </pros>
      <cons>
        ONE-WAY and strictly more lossy than redacting: it throws away the path and the parameter
        names, which is the analytic value the operator explicitly chose to keep at UAT. Historical
        sightings vanish from the edge table; the `artifacts` row and its `seen_count` survive, so
        the plugin still knows the bytes were seen, just not where.
      </cons>
    </option>
    <option id="leave">
      <name>Leave them; they age out under STORE-06's 90-day bound</name>
      <pros>
        No code, no risk, and reversible in the only sense that matters — the values still exist, so
        any of the other two options remains available later. Defensible if task 1 measured zero or
        near-zero affected rows, which is plausible given that this plugin has not shipped and the
        isolated Phase 1 instances are torn down by `instance.sh`.
      </pros>
      <cons>
        The exposure stands for up to 90 days in a file that survives project deletion and
        force-reinstall. It also leaves the column in two states — some rows redacted, some not —
        which is a trap for anyone who later reads the column and assumes one shape. If chosen, the
        90-day window must be written into the SUMMARY and STATE.md as an accepted, dated risk with
        the measured row count beside it, not left implicit.
      </cons>
    </option>
  </options>
  <resume-signal>Select: redact-in-place, purge, or leave</resume-signal>
</task>

    **If `redact-in-place` was selected:** add two SQL constants to `observations.ts`.

    The selector: a `SELECT` of `project_id, sha256, request_id, url` from `observations` where
    `project_id = ?` AND the url is `LIKE` a pattern containing `?` AND `LIKE` a pattern containing
    `=` AND `NOT LIKE` a pattern containing the redaction marker, with a `LIMIT ?`. Those three
    conditions together are what makes the sweep CONVERGE, and the reasoning belongs in a comment
    beside them because it is not obvious: requiring `=` excludes a bare-flag query such as `?debug`,
    whose redaction is a no-op and which would therefore be selected on every pass for ever;
    requiring the marker's ABSENCE excludes rows a previous pass already handled. Every row the
    predicate selects is rewritten into a form the predicate no longer matches, so repeated passes
    terminate. `project_id = ?` is in the WHERE clause and not merely in the column list — the
    `unscoped-multi-row` rule was written after a mutation proved a column-list match let a
    cross-project read through.

    The writer: an `UPDATE observations SET url = ? WHERE project_id = ? AND sha256 = ? AND
    request_id = ?` — the full primary key, so it can only ever touch the one row read. One
    statement, positional `?` only, prepared inside the write, parameters spread into `run()`.

    The marker literal appears inside the selector's SQL as text while `QUERY_VALUE_REDACTION` is a
    TypeScript constant, and SQL cannot be interpolated here without failing the `interpolated-sql`
    rule. That is a genuine drift hazard: change the constant and the selector silently stops
    matching anything, which reads exactly like "nothing to do". Close it with an assertion in
    `observations.spec.ts` that the selector SQL string contains `QUERY_VALUE_REDACTION`'s value, and
    say in a comment that the assertion is the reason the duplication is tolerable.

    Export `redactStoredObservationUrls(db, projectId, limit = RETENTION_SWEEP_MAX_ROWS)` returning
    `{ examined, rewritten, errors, lastError, moreWork }` — the same shape `sweepRetention` returns,
    for the same reason: WR-09 established in this codebase that a sweep which discards its errors
    discards the only account of why it stopped working. Rewrite a row only when its redaction
    DIFFERS from what is stored, so `rewritten` counts real changes and cannot be inflated by a no-op
    write. Set `moreWork` when the pass filled its limit. Every error goes through the same recording
    path; none may fail uncounted.

    **If `purge` was selected:** add ONE SQL constant, in EXACTLY this form and no other —
    `DELETE FROM observations WHERE rowid IN (SELECT rowid FROM observations WHERE project_id = ?
    AND <the same three-part url predicate> LIMIT ?)`. Export
    `purgeUnredactedObservations(db, projectId, limit)` returning the same summary shape. No selector
    round trip, no per-row read.

    The form is prescribed rather than left open, and the reason is a real portability trap. The
    obvious spelling — `DELETE FROM observations WHERE … LIMIT ?` — requires SQLite to have been
    compiled with `SQLITE_ENABLE_UPDATE_DELETE_LIMIT`. This phase measured `sqlite_version()` inside
    Caido (plan 01-01 truth #8) but it did NOT measure that compile flag, so the natural reading may
    simply fail to parse on the target build. That is a bad thing to discover while executing an
    operator's irreversible decision. The `rowid IN (SELECT … LIMIT ?)` form needs no compile flag,
    is bounded the same way, and keeps `project_id = ?` in the inner predicate where
    `sql-discipline`'s `unscoped-multi-row` rule reads it — repeat `project_id = ?` in the OUTER
    predicate as well if the gate reports the outer DELETE unscoped, and record which spelling the
    gate actually accepted in the SUMMARY rather than leaving the next reader to re-derive it.

    Still assert that the DELETE's predicate contains `QUERY_VALUE_REDACTION`'s value: the marker
    drift hazard is identical here — a changed constant makes the predicate match nothing, which
    reads exactly like "nothing to purge".

    **For both sweep branches**, wire it into `runRetentionPass` in `consumer.ts`, inside the existing
    `try` and alongside the existing `sweepRetention` call — the cadence, the project scoping, the
    epoch re-check and the outer catch are all already correct there and adding a second scheduling
    mechanism would be two things to keep in step. Fold its errors into `counters.storeErrors` and
    `recordError` exactly as the retention summary's are, with its own log prefix.

    Add one counter to `telemetry.ts`'s `Counters` type and `createCounters`:
    `observationUrlsRedacted` for the redact branch, `observationUrlsPurged` for the purge branch.
    Check the chosen name against `FORBIDDEN_COMPLETENESS_WORDS` before writing it — `telemetry.spec.ts`
    enforces that list word-by-word over counter identifiers and a name containing a completeness word
    fails there, not here.

    Add to `consumer.spec.ts` a case in the STORE-06 describe block that seeds observation rows
    carrying verbatim query values through a path that bypasses the redactor, runs the consumer past
    the cadence boundary, and asserts the rows are clean afterwards WITH NO DIRECT CALL to the sweep
    anywhere in the test — the same shape as the existing "row counts FALL with no call to
    sweepRetention anywhere in this test" case. Availability is not scheduling and only that shape
    tells them apart.
