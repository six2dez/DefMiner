<objective>
Close UAT gap 2. The outbound gate — CORE-11's from wave 10, CORE-01's when it was written — is real,
wired, and mutation-proven — the verifier planted
`sdk.requests.send(req)` into the real `hooks/passive.ts` and watched it go red naming the file, the
surface and the reason. It also probed 22 shapes and **14 were missed**, several of them the idiomatic
way to write the call.

The gate's own truth claim is "a call to `sdk.requests.send` ANYWHERE in a non-spec module fails a
gate". Its actual rule is "no module writes four specific spellings". These reported ZERO violations,
executed, not argued:

    globalThis.fetch(u)                      window.fetch(u)         (globalThis as any).fetch(u)
    const { requests } = sdk; requests.send(q)                       let r; r = sdk.requests; r.send(q)
    sdk.requests.send.call(...) / .apply(...)                        Reflect.apply(sdk.requests.send, ...)
    const s = sdk.requests.send; s(q)        sdk.requests.sendRaw(q) const m = "send"; sdk.requests[m](q)
    const r = "requests"; sdk[r].send(q)     await import("caido:" + "http")
    new XMLHttpRequest().send()              new WebSocket("wss://…")

Purpose. `globalThis.fetch` is the sharp one: `packages/backend/src/telemetry.ts:289` already reaches
`globalThis.performance` through exactly that idiom, because that is what you do in a runtime where
you cannot assume a bare global exists — so the codebase's own established way of reaching a global is
the single form the gate cannot see. `const { requests } = sdk` is ordinary TypeScript and the gate
already handles the INNER destructure, so its absence reads as an oversight rather than a boundary.
And `packages/engine/src` ships in the bundle, is imported by `index.ts`, `consumer.ts` and
`lifecycle.ts`, and is walked by NO outbound gate at all — including `pipeline.ts`, the module whose
job is "no speculative retrieval", which is the literal wording of the requirement.

Three Phase 0 measurements make a regression here worse than it sounds, and they have not changed:
`SURFACES_FIRING_INTERCEPT = "proxy"`, so traffic this plugin generated is invisible to this plugin and
no counter anywhere would move; `sdk.requests.send()` does not re-fire the hook under any
save/plugins combination, so there is no self-observation to fall back on; and `caido/caido#2211` was
filed against the exact target build, where cumulative sends abort `caido-cli` with the operator's real
project data.

Output: the same gate, at the reach its own header claims, over both source roots, with every missed
shape as an executed fixture and three mutations run against real shipped modules.

**Why this plan retags the gate to CORE-11 itself, rather than a later plan doing it.** The id is
opened by plan 01-10 task 3 in wave 10 — before this plan declares it — because a plan must declare
the requirement it enforces and frontmatter is what a verifier reads. The gate's own strings are a
different edit: they live in the header, in the rule table's `why` fields and in the `add()` failure
text, and task 1 rewrites all three regions anyway. Doing the retag in a later plan would mean two
plans editing one header two waves apart, which is exactly how the second silently reverts the first —
the reason 01-11 gives for not letting two plans touch one `schema.spec.ts` paragraph. So the ledger
half is upstream, the source half is here, and neither one is left for later.

**Why wave 12, serialised behind 01-11, when `files_modified` overlap with every other new plan is
zero.** Verified pairwise: this plan touches `outbound-prohibition.spec.ts` and `COVERAGE.md` and
nothing else, so the wave guard would have allowed it beside 01-10, 01-11 and 01-13. The coupling is
one axis over and the wave guard does not model it — task 2 plants outbound calls into
`hooks/passive.ts` and `packages/engine/src/pipeline.ts`, rebuilds `dist/`, and asserts the whole suite
is green, while 01-10 and 01-11 are reverting redaction branches in the same tree and asserting the
same thing, and 01-13 is planting an `e.message` render. Run concurrently, each plan's mutation window
makes another's whole-suite assertion fail for an unrelated reason, intermittently and misattributed to
whichever plan read the tree at the wrong moment. A phase whose entire subject is gates that can fail
honestly cannot afford a gate that fails dishonestly. `depends_on: [01-11]` is a SEQUENCING edge, not a
code dependency — recorded in words so nobody reads the empty overlap and optimises it into a shared
wave.

**Why there is no leading `type="tracer"` task.** `TRACER_MODE` is on. This plan widens one static gate
over already-shipped code; there is no path through the stack to wire and nothing end-to-end to prove.
The mutation runs in task 2 are the equivalent evidence and they are stronger for this kind of work.

**What this plan deliberately does NOT do.** `scripts/ci/check-bundle-imports.mjs` is not touched, per
decision P9-D2: its allowlist answers "which specifiers Caido's QuickJS resolved WHEN MEASURED", and
`caido:http` is on it because the Phase 0 probe loaded it successfully. Removing an entry would
silently redefine that file's semantics from "measured loadable" to "permitted", which is a lie about a
measurement — the policy belongs in a source gate, and this is it. `COVERAGE.md` dispositions, rows,
counts and the INTEGRATE/OPT-OUT split are not changed; only three justification cells in each of the
two tables. And no existing PLAN.md is amended.
