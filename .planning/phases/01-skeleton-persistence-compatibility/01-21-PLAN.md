<objective>
Close WR-24 and fold in IN-22: the STORE-07 gate is blind to the OPERATOR class of render — `? :`, `??`
and `||` — and the residual it re-derived in the same commit as its last widening does not name it.

Purpose. `derivesFrom` unwraps parentheses, casts, non-null assertions, member access and member calls,
then requires an identifier at the bottom. A `ConditionalExpression`, a `??` and a `||` are none of
those, so the descent stops and the render is invisible. Executed against `auditSource("store/x.ts",
src)`:

```
catch(e){ return { ok:false, error: e.message }; }                            ["unredacted-object-value"]
catch(e){ return { ok:false, error: e instanceof Error ? e.message : "x" }; } []
catch(e){ return { ok:false, error: e.message ?? "x" }; }                     []
catch(e){ return { ok:false, error: e.message || "x" }; }                     []
```

`e instanceof Error ? e.message : String(e)` is not an exotic spelling. This repository enables
`useUnknownInCatchVariables`, the gate's own header cites that setting as the reason cast forms matter,
and narrowing a caught `unknown` before rendering it is exactly what the setting pushes an author
toward. It is likelier in a Phase 2 `finishAnalysis` than either of the two accumulator idioms WR-17
just added.

**What makes it a finding rather than a gap is the paragraph shipped in the same commit.** WR-17's fix
rewrote the render-form list and added a residual "RE-DERIVED against the widened rules rather than
carried forward", enumerating two classes: a render through an unnamed method, and an accumulator that
is neither a `+=` nor a `.push`. The class that is actually open is a third — an OPERATOR between the
binding and the render position. A residual list that announces it was re-derived is trusted for its
completeness, which is the argument `schema.spec.ts`'s OPEN list already makes about itself one
directory away.

**AND THIS IS A WIDENING, NOT A CORRECTION OF A LIE — the plan states that plainly and does not inflate
it.** The render-form list says in its own words that it is an ENUMERATION and "does not claim to be
closed"; what it claims is that everything on it is executed below. The verifier scored WR-24 a warning
for exactly that reason and drew the distinction explicitly against the `schema.spec.ts`-style overclaim
that makes a blocker. Writing this up as a correction of a false claim would be the same dishonesty in
the opposite direction, in the round whose entire subject is claims outrunning evidence.

**SEVERITY, STATED HONESTLY.** Nothing leaks today: the verifier recorded zero residual bare
stringification under `packages/backend/src/store`, and the surviving renders outside that scope each
carry a named owner with a checkable requirement id. This is a gate that would stay quiet on a render
somebody writes in Phase 2.

Output: three operator branches in the function that already descends five, every executed shape as a
failing fixture with its safe twin, and a residual re-derived a third time that names what is left.

**Why wave 21, and why serialised.** Every gap-closure plan in this phase since 01-09 has been
serialised for one reason that still holds exactly: this plan mutates the shared working tree to prove
its fixtures can fail, while asserting the whole suite green, and a concurrent plan's red is

**What this plan deliberately does NOT do.** It does not touch
