<objective>
Expand the tracer's single admitted path into the full ingestion pipeline: a complete admission decision with
a named reason for every rejection, a bounded queue with a visible overflow count, an overlapping chunker that
carries absolute offsets, a temporal yield, and a wall-clock deadline that degrades to a recorded partial state
rather than freezing the one thread this runtime has.

Purpose: three of these are places where the obvious implementation succeeds silently while doing nothing.
Yielding with `setImmediate` or `Promise.resolve()` scored a 0.00 timer service ratio — identical to a fully
blocking loop — so only `setTimeout(fn, 0)` yields. Yielding per 64 KiB chunk costs 330.7% overhead over 137
yields against 21.2% over 5 at a 25 ms temporal budget, so the geometry serves matching windows and the clock
serves the yield. And a content-type-keyed gate silently classifies every 304 as non-script, when a 304 reaches
the hook with a zero-length body and **no content-type header whatsoever** and is in fact a revalidation of a
bundle we may already know.

This plan is also where **every store call site in the plugin lives**. The consumer is the only writer, so
the artifact upsert, the observation write, CORE-08's skip decision and STORE-06's retention schedule are all
wired here, against signatures plans 01-01 and 01-04 have already settled. That is why this plan runs in
wave 4 rather than beside 01-04 in wave 3: a store module and its only caller being rewritten by two plans in
parallel is a contract break no `files_modified` overlap check can see, because the shared mutable resource is
a function signature rather than a file. Serialising costs one wave of parallelism and removes the entire
class of failure.

Output: six engine modules and two hook modules, each unit-tested under plain vitest with no Caido present,
the fake SDK that makes backend logic testable at all, and a consumer in which every persistence path the
phase promises is actually reachable from a running plugin.
</objective>

## Flagged Planner Assumptions (edge-probe `unclassified`, unresolved)

- **CORE-02 (unclassified)** — assumed: the four gate axes are evaluated in the order status, size, kind, scope,
  and the FIRST failing axis names the rejection reason. This matters because a 304 fails on status, size and
  kind simultaneously, and only a status-first ordering gives it an honest reason. Also assumed: `Body.length`
  is the size axis (decompressed identity bytes, per `SIZE_GATE_SOURCE`), read as a property with no decode.
- **CORE-04 (unclassified)** — assumed: "exactly one CPU consumer" means one drain loop per plugin runtime, not
  one per project and not one per queue. `Worker` is `undefined` in this runtime, so there is no way to have
  more than one thread; the invariant being enforced is that no second *loop* is started re-entrantly.
