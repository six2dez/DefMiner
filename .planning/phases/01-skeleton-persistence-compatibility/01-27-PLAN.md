<objective>
Replace the hand-authored residual with one DERIVED from the gate's own code, and add a test that goes
RED when the derived text and the shipped text disagree in either direction.

Purpose. Waves 23 through 26 each closed a genuine instance. None of them changes the mechanism that
produced all four. The gate's stated bound has now been wrong in five consecutive rounds, every time
because a human wrote a sentence claiming a bound nobody re-derived from the code, and every time the
correction was itself a hand-written sentence. CR-09 is the sharpest form of it: the residual written
in round 4 TO REPLACE the previous false one was itself false, and was copied verbatim into
`REQUIREMENTS.md:46`, which is the text CORE-11's `[x]` was flipped against.

**The mechanism, stated as three bindings.** A registry of resolver records, each naming a mechanism in
the walk, the shapes it reads, a probe source and the rule identifiers that probe produces. A pure
function that renders the residual text from that registry. And three tests: one that executes every
probe against `auditSource` and asserts its row — which binds the REGISTRY to the CODE; one that reads
each shipping surface's own bytes, extracts the block between sentinels and compares it to the rendered
text — which binds the TEXT to the REGISTRY; and one that reads the gate file's own source for
collectors matching a declared naming convention and asserts each has a row — which makes an
UNREGISTERED mechanism detectable rather than invisible.

**After this plan, drift is a failing test rather than a reviewer's finding.** Editing the prose
without the code turns the suite red. Changing the code without the registry turns the suite red.
Changing the registry without regenerating turns the suite red. Adding a collector with no row turns
the suite red. Each of those four is proven by an executed mutation and not by this paragraph.

**WHAT A DERIVED RESIDUAL CANNOT PROVE, AND THIS IS NOT A CAVEAT — IT IS PART OF THE DESIGN.** It can
state which shapes each REGISTERED resolver reads, and that statement is verified by execution. It
cannot prove the registry ENUMERATES every mechanism: the coverage guard sees only collectors matching
the naming convention it declares, and `isAssembledKey`, `isProvablyNumeric`, `keyReceiver`,
`receiverKind` and `unwrap` are functions, hand-registered, outside that guard. It cannot prove each
row's probes cover that resolver's whole DOMAIN — a probe is an example, and an example proves the row
is true of itself. It cannot prove the SILENCE list is complete: a shape nobody thought of is still
silent and still unlisted. What it does is move the question from "is this sentence true?" — which five
rounds answered wrongly — to "is this registry complete?", which is smaller, mechanical, and partly
guarded. **This plan is not the end of the class and no artifact it writes may say it is.** Saying so
would be the sixth instance of exactly the defect it exists to reduce.

**Which surfaces the derived text FEEDS, decided here and stated in every one of them.**

- `packages/backend/src/outbound-prohibition.spec.ts` — DERIVED, byte-checked. It is the source of
  truth and the generator lives beside it.
- `.planning/REQUIREMENTS.md` CORE-11 — DERIVED, byte-checked. It is the text a requirement's
  completion is read against and it is the copy that drifted through five rounds. A pointer here would
  leave the ledger a reader trusts most as the one surface that can still be wrong.
- `.planning/STATE.md` — POINTER, prose. An append-only dated decision log. A block regenerated inside
  it would rewrite the record of what was believed and when, which is the only thing that makes it
  readable.
- `.planning/WINDOWS.md` — POINTER, prose, through the tool. Same reason, plus it is tool-owned and a
  test binding a specific entry's description to generated text would break the moment a later phase
  appends or closes an entry.

**SEVERITY, STATED PLAINLY.** Nothing leaks. No outbound call exists in any non-spec source under
either root, the gate runs green over the real tree, and `check:bundle` reports one specifier,
`crypto`. This plan changes no rule and adds no widening; it changes how the residual is produced and
checked.

Output: a residual nobody writes, bound to the walk by execution and to its shipping surfaces by bytes,
with its own limits stated inside it.

**Why wave 27, and why serialised.** The registry's probe expectations must be written against the gate
as waves 23 through 26 left it — a registry written against an older gate would be born stale, which is
the failure this plan exists to prevent, at the moment of its own construction. It also plants four
deliberate mutations in shared files, which needs a quiet tree.

**What this plan deliberately does NOT do.** It changes no rule and closes no shape: every widening in
this round landed in waves 23 through 26. It does not flip CORE-11's checkbox — wave 28 owns that, and
flips it against this block. It does not touch `packages/backend/src/store/*`, `tests/pins.spec.ts` or
`scripts/phase1/tracer-e2e.sh`. It modifies no plan 01-01 through 01-26, and no `01-VERIFICATION.md`,
`01-REVIEW.md` or `01-UAT.md`.
</objective>
