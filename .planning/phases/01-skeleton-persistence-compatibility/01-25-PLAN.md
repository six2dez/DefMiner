<objective>
Read a conditional, `??`, `||` and `&&` in CALL-RECEIVER position the way key position and initializer
position already read them, and collapse the three copies of that idea into one.

Purpose. Round 4 added conditional handling in KEY position and argued for it on exactly the right
grounds: `sdk[b ? "requests" : "net"]` hides nothing — both keys are string literals naming outbound
receivers — so it resolves to a NAMED receiver and reports `outbound-send`, and calling a completely
readable site unreadable would be an overclaim running the other way. The identical argument applies
to the receiver expression itself, and that spelling is silent:

```
(b ? sdk.requests : sdk.net).send(req)                   []
(sdk.requests ?? sdk.net).send(req)                      []
(sdk.requests || sdk.net).send(req)                      []
sdk[b ? (c ? "requests" : "x") : "y"].send(req)          []
```

while the two controls added in the SAME round both report:

```
const r = b ? sdk.requests : sdk.net; r.send(req)        ["outbound-send"]   // initializer position
sdk[b ? "requests" : "net"].send(req)                    ["outbound-send"]   // key position
```

**The mechanism is one function.** `initializerReceiver` at ~`:1264` unwraps a `ConditionalExpression`.
`receiverKind` at ~`:1196` — the function the property-access rule calls on the callee's receiver —
does not, so a conditional written directly in call position falls through every branch and returns
`undefined`, which every caller reads as "not a receiver". The nested-key line is the same gap inside
`keyReceiver`, whose docblock at ~`:1160-1170` claims it is the single definition of what a readable
key is, "called from the direct key and both conditional branches, so they cannot disagree about what
the walk can read" — `keyReceiver` does not itself handle a conditional, so the two do disagree the
moment a conditional appears inside one.

**Nothing anywhere discloses it.** THE FINAL RESIDUAL enumerates two hops of key, a function boundary,
a parameter, a loop binding, another file and the `NUMERIC_MEMBERS` heuristic. A conditional receiver
in call position is none of those. Both shapes are one expression, in this file, with every operand a
literal or a `requests`/`net` member.

**HOW THIS IS FRAMED, AND THE FRAMING IS DELIBERATE.** This is a WIDENING of an enumeration that
declares itself open, not the correction of a false sentence. Round 4's wave 21 framed WR-24 that way
and the verifier credited it. The distinction matters in both directions: CR-09 was a residual that
asserted something false, while WR-27 is a residual that omitted a shape entirely — the second is the
weaker finding and this plan says so rather than borrowing the first's weight. What it does NOT get to
say is that an omission is harmless: a residual list is trusted for its completeness, and a reader
enumerating what this gate misses would have finished the list and stopped.

**SEVERITY, STATED PLAINLY.** Nothing leaks. No outbound call exists in any non-spec source under
either root, the gate runs green over the real tree inside a 1105-test suite, and `check:bundle`
reports one specifier, `crypto`. WR-27 is a prospective blindness in a test-only gate. No sentence
written by this plan may imply otherwise.

Output: one operator descent, reached from all three positions, with the three copies collapsed to the
one its own docblock says was the goal.

**Why wave 25, and why serialised.** It shares `outbound-prohibition.spec.ts` with plans 01-23 and
01-24 in the two waves before it, and it must land after CR-10 because the key resolver it recurses
through is the one wave 24 rewrote. Beyond the file overlap, this plan reverts operator branches in
turn to prove each is load-bearing, which needs a quiet tree.

**What this plan deliberately does NOT do.** It does not close IN-26, the destructured key binding
(wave 26 owns it). It does not touch `packages/backend/src/store/*`, `tests/pins.spec.ts` or
`scripts/phase1/tracer-e2e.sh` (wave 26). It does not build the derivation machinery (wave 27), does
not amend `REQUIREMENTS.md` or `STATE.md`, and does not flip CORE-11's checkbox (wave 28). It modifies
no plan 01-01 through 01-24, and no `01-VERIFICATION.md`, `01-REVIEW.md` or `01-UAT.md`.
