<objective>
Bind a registry row's CLAUSE to the BRANCHES it names, by execution, so the mutation the verifier ran
turns the row red instead of nothing at all.

Purpose. Round 5's derived residual is the best mechanism this phase has produced and the verifier
proved two of its three bindings real: the shipped TEXT is bound to the REGISTRY by bytes, and each
row's PROBE is bound to the walk by execution. The third binding does not exist. A row's `clause` is
hand-written prose that no assertion reads, and the verifier proved it by deleting the
`PlusEqualsToken` assembly branch — a branch `assembledNames`' clause names in so many words — and
watching the entire derived block stay at 52 passed, 0 failed. Only one hand-written fixture 1,400
lines away went red. **The generated preamble's point 1 is false at branch granularity, and point 3
three lines below it already states the honest version.**

That is why CR-11, CR-12 and CR-13 could all land inside a mechanism that is 100% green: each is a
clause whose stated reach exceeds its probe's executed reach — the phase's recurring failure mode,
reproduced one level up, in the artefact built to end it.

**This plan is WR-32's stronger fix, and the reviewer named both options.** The cheap repair was to
delete point 1's falsified half; the stronger one was a per-row branch field naming the code sites each
clause covers, with one probe per named branch, so the mutation the verifier ran turns the row red.
This plan takes the stronger one and corrects point 1 as well, because a mechanism that supports the
stronger claim should make the claim rather than withdraw it.

**The mechanism, stated as three additions.** A `branches` list on `ResolverRecord`, each entry
naming the clause phrase it answers, the code site it was read off, a probe and the measured rule
identifiers. A frozen `BRANCH_VOCABULARY` of branch-naming phrases, so "this clause names that
branch" is a string test rather than a reading, with a guard that fails when a phrase present in a
clause has no branch answering it. And a `QUANTIFIED_CLAUSES` list for the clauses that name no
branch because they assert a UNIVERSAL — every unbounded quantifier must carry a measured statement
of what bounds it, which is the exact shape of both CR-11 and CR-13.

**After this plan, a branch removed from the walk turns its own ROW red.** Proven by reproducing the
verifier's mutation, not by this paragraph. Four further mutations prove the guard's other failing
paths: a second named branch deleted, a branch entry removed from a row whose clause names it, a
`branches` list emptied, and an unbounded quantifier added with no declared bound.

**WHAT CLAUSE-TO-BRANCH BINDING STILL CANNOT PROVE, AND THIS IS PART OF THE DESIGN RATHER THAN A
CAVEAT.** It proves each NAMED branch has an executed probe. It cannot prove the clause NAMES every
branch the code has — a branch the clause is silent about is bound to nothing, exactly as before. It
cannot prove `BRANCH_VOCABULARY` covers every way a branch can be named in English; a clause phrased
outside the vocabulary is unmatched and therefore unbound, and the guard's own count is what makes a
vocabulary that stops matching visible. And it cannot prove the registry ENUMERATES every mechanism,
which the existing point 2 already states. It moves the question from "is this clause true?" to "does
this clause name its branches in the declared vocabulary?" — smaller, mechanical, and not zero.
**This plan is not the end of the class and no artifact it writes may say it is.**

**Where a clause names a branch the code does not have.** That is CR-11, CR-12 and CR-13, and this
plan does NOT widen the code for any of them. It corrects the clause to its MEASURED reach, preserves
the falsified phrase with a dated FALSIFIED marker and the finding id, and names the wave that owns
the widening — 30 for CR-13, 31 for CR-12, 32 for CR-11. Those waves must then re-add the phrase AND
its branch probe in the same commit as the code, which is what makes their widenings provable at
branch granularity rather than at fixture granularity.

**SEVERITY, STATED PLAINLY AND NOT INFLATED.** Nothing leaks. No outbound call exists in any non-spec
source under either root, the gate runs green over the real tree inside a 1200-test suite,
`check:bundle` reports the shipped bundle's entire import set as one specifier (`crypto`), and the
redaction half survived 16,160 swept inputs with zero secret survivals. Every finding this plan
addresses is PROSPECTIVE blindness in a test-only gate. This plan changes no rule and adds no
widening.

Output: a registry whose clauses are bound to their branches by execution, with the mutation that
exposed the gap reproduced as the proof, and with the three things the binding still cannot prove
stated inside the text it generates.

**Why wave 29, and why serialised.** The branch probes must be measured against the gate as wave 28
left it; a branch list written against an older gate would be born stale, which is this plan's own
subject. It also plants five deliberate mutations in shared files, which needs a quiet tree. Waves 30,
31 and 32 all depend on the `branches` field existing, so it must land first.

**What this plan deliberately does NOT do.** It changes no resolver and closes no shape. It does not
flip CORE-11's checkbox and does not argue that it could be flipped — wave 32 owns that, against a
discharge table whose every row is discharged. It does not touch `packages/backend/src/store/*`,
`tests/pins.spec.ts` or `scripts/phase1/tracer-e2e.sh`. It modifies no plan 01-01 through 01-28, and
no `01-VERIFICATION.md`, `01-REVIEW.md` or `01-UAT.md`.
