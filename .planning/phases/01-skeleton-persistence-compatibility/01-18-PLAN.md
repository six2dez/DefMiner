<objective>
Close CR-08: make the CORE-11 gate read a receiver key in every spelling it is capable of reading,
and make its five disclosures agree with each other and with the code.

Purpose. The finding is not that the gate has a bound — a bound is fine and this one was set by a real
measurement. The finding is that the gate's stated reach is WIDER than its executed reach, for the
fourth review running, in the file that was rewritten for exactly this defect one wave ago. Boundary 2
says an assembled receiver key "is reported wherever that value is used as one, including through a
one-hop binding". One `const` disproves it. The verifier executed the positive control first, which is
what makes the empty lists real rather than a fixture artefact:

```
const r = "requests";              sdk[r].send(req)                ["outbound-send"]        <- reads sdk[…]
                                   sdk["req"+"uests"].send(req)    ["outbound-unanalysable"]
const k = "req"+"uests";           sdk[k].send(req)                []
let   k = `req${"uests"}`;         sdk[k].send(req)                []
const k = ["req","uests"].join(""); sdk[k].send(req)               []
const k = g();                     sdk[k].send(req)                []
                                   sdk[b ? "requests" : "net"].send(req)   []
                                   sdk[(0,"requests")].send(req)           []
```

And the gate gets the identical defect RIGHT one level down (`const m = "se"+"nd";
sdk.requests[m](req)` reports) and right on the global path (`const k = "fet"+"ch"; globalThis[k](url)`
reports). The asymmetry is specific to the RECEIVER key, which is the exact asymmetry WR-19 was raised
to remove, standing one level up.

**The conditional is the sharper half and it is undisclosed everywhere.** `sdk[b ? "requests" : "net"]`
hides nothing. Both keys are string literals naming outbound receivers. `initializerReceiver` — one
function away in the same closure — already resolves a conditional when it appears in INITIALIZER
position, and does it for this exact reason. So this is a site the walk can read COMPLETELY, reported
by nothing and disclosed by nothing, under a requirement whose text says "in any spelling".

**SEVERITY, STATED HONESTLY, AND THE PLAN'S PROSE MUST NOT DRIFT FROM THIS.** Nothing leaks today. The
gate runs green over the real tree in the full 1044-test suite, `pnpm check:bundle` reports the shipped
bundle's whole import set as one specifier (`crypto`), and no outbound call exists in any non-spec
source under either root. This is a PROSPECTIVE blindness — a gate that would stay green on a call site
somebody writes next year. It is materially less severe than round 2's blocker, which was a whole HTTP
Basic credential sitting in a durable column. It is a blocker on the claim-versus-enforcement standard
this phase set for itself, not on a live secret, and no sentence written by this plan may imply
otherwise.

**The trap this plan exists to avoid, stated before anything else.** The verifier found that the ONE
fixture which looks like a bound on the assembled-key rule — `:1740-1744`, `const r = "requests";
sdk[r].send(req)`, under the sentence "The ONE-hop version of the same shape is caught, which is what
makes the residual a bound rather than a hole" — resolves through `constStrings`, a completely
different mechanism, so it is green whether or not `isAssembledKey` can see a hop. Adding fixtures is
therefore not enough. Each new fixture must be tied to the mechanism it exercises, each mechanism must
be named in the header, and each must be shown RED by reverting the branch that enforces it. A fixture
that passes through a different code path than the rule it claims to bound is worse than no fixture,
because it is read as a bound.

Output: a key resolver that reads what it can read; the eight executed shapes as fixtures whose failing
paths have been run; a mechanism-to-shape table in the header; and one bound written in five places
that currently disagree.

**Why wave 18, and why serialised.** Every gap-closure plan in this phase since 01-09 has been
serialised, deliberately, and the reason still applies exactly: this plan mutates the shared working
tree to prove its gates can fail, while asserting the whole suite green. A concurrent plan's red is
indistinguishable from this plan's own. It also shares `outbound-prohibition.spec.ts` with plan 01-19
one wave later.

**What this plan deliberately does NOT do.** It does not close WR-23 (`const e = eval; e(s)`), WR-26
(`isProvablyNumeric`'s docblock) or IN-20 (`const g = globalThis`) — plan 01-19 owns all three, in the
same file, one wave later, and splitting them keeps each plan's mutation proofs isolated and each
plan's context inside its budget. It does not mark CORE-11 `[x]`: that flips in 01-19 once the last
enumerated shape is enforced, and this plan records the reason it is staying open ON the requirement.
It does not touch `packages/backend/src/store/*` — plans 01-20 and 01-21 own WR-22 and WR-24. It does
not touch `tests/pins.spec.ts` or `scripts/phase1/tracer-e2e.sh` — plan 01-22 owns WR-25 and IN-21. It
does not run a live Caido: this is a static-gate round and no run directory is produced. It modifies no
plan 01-01 through 01-17, and no `01-VERIFICATION.md`, `01-REVIEW.md` or `01-UAT.md`.
