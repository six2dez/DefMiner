<objective>
Make the string-key collectors describe a name's bindings across the file rather than only its first,
so a harmless literal stops shadowing every later rebinding of the same name.

Purpose. `keyReceiver` at ~`:1172` calls `literalOf(key)` first — deliberately, and the ordering
comment at ~`:1160-1170` is sound on its own terms — and `literalOf` resolves an identifier through
`constStrings`. `constStrings` is written ONLY at the VariableDeclaration branch (~`:1398`) and never
at the assignment branch (~`:1454-1481`). So a name whose declaration bound a harmless literal
resolves to that literal forever, and `isAssembledKey` and `assembledNames` beneath it are unreachable
for that name. Executed by the verifier:

```
let k = "harmless"; k = "requests";      sdk[k].send(req)      []
let k = "harmless"; k = "req"+"uests";   sdk[k].send(req)      []
let k = "req";      k += "uests";        sdk[k].send(req)      []
var k = "harmless"; k = "requests";      sdk[k].send(req)      []
let k = "harmless"; k = "fetch";         globalThis[k](url)    []
```

and the controls that prove these are genuine misses rather than a fixture artefact — **the same
assignment fires when no string initializer precedes it**:

```
let k;      k = "requests";     sdk[k].send(req)     ["outbound-send"]
let k;      k = "req"+"uests";  sdk[k].send(req)     ["outbound-unanalysable"]
let k = 1;  k = "req"+"uests";  sdk[k].send(req)     ["outbound-unanalysable"]
let k;      k = "fetch";        globalThis[k](url)   ["outbound-unanalysable"]
```

**The site is completely readable.** In the first silent line both strings are string literals sitting
in the AST twelve tokens apart. This is not a value the walk cannot follow; it is a value the walk
reads and then discards in favour of a stale one. That distinction is the one residual (b) is built
on — the walk reports what it can see being HIDDEN and discloses what it merely cannot FOLLOW — and
this falls on the reporting side of it.

**Two sentences written last round are falsified by it.** Boundary 2 at `:83-85` states that file-wide
bindings over-approximate rather than under-approximate, "a name bound to an outbound receiver
anywhere in the file is treated as one everywhere in it" — here `k` IS bound to `"requests"` in the
file and is treated as one NOWHERE, which is the direction a reader is told cannot happen. And
`:127-130` says the assembled key resolves through either a declaration or an assignment; the
assignment spelling is defeated by any preceding string initializer, and the collector's own comment
at ~`:1476-1478` claims it is covered by construction.

**The `+=` line is the sharpest.** The sibling gate one directory away learned this specific lesson
already: WR-17 widened `error-redaction.spec.ts` to `+=` on the argument that it is one token away
from a form already covered. Here the header claims assembly is read in every spelling.

**THIS FIX HAS A MIRROR AND THE PLAN REFUSES TO LEAVE IT UNMEASURED.** Any mechanism that makes a
later binding visible has to answer what happens to `let k = "requests"; k = "harmless";`. A
last-binding-wins mechanism silences it — a NEW under-approximation created by the fix. An
any-binding-wins mechanism reports it — an over-approximation that must be measured against the real
tree before it is accepted. The plan does not choose for the executor. It requires the choice to be
made by measurement, the mirror shape to be asserted in whichever direction it lands, and the direction
to be disclosed in the same commit. A fix whose own mirror is undiscovered is next round's finding.

**SEVERITY, STATED PLAINLY.** Nothing leaks. No outbound call exists in any non-spec source under
either root, the gate runs green over the real tree inside a 1105-test suite, and `check:bundle`
reports one specifier, `crypto`. CR-10 is a prospective blindness in a test-only gate. No sentence
written by this plan may imply otherwise.

Output: collectors that describe the current state of a name rather than its first, both directions
measured, and a disclosure that names which direction each mechanism errs in.

**Why wave 24, and why serialised.** It shares `outbound-prohibition.spec.ts` with plan 01-23 one wave
back, and it must land after the residual is true — narrowing a false sentence produces a narrower
false sentence. Beyond the file overlap, this plan reverts collector branches in turn to prove each is
load-bearing, which needs a quiet tree.

**What this plan deliberately does NOT do.** It does not close IN-26, the destructured key binding,
even though the review says it is the same two lines. Wave 26 owns it, for a stated reason: a
destructure widening landing in the same commit as the rebinding widening makes the per-branch mutation
attribution ambiguous, and the round-4 lesson is that combined mutations hide which branch is doing the
work. It does not touch `receiverKind`'s conditional handling (wave 25 owns WR-27). It does not touch
`packages/backend/src/store/*`, `tests/pins.spec.ts` or `scripts/phase1/tracer-e2e.sh` (wave 26). It
does not build the derivation machinery (wave 27), does not amend `REQUIREMENTS.md` or `STATE.md`, and
does not flip CORE-11's checkbox (wave 28). It modifies no plan 01-01 through 01-23, and no
`01-VERIFICATION.md`, `01-REVIEW.md` or `01-UAT.md`.
