<objective>
Close the half of UAT gap 1 that the verifier reproduced by execution: `?ghp_AAAA…` — a bare query
segment with no `=`, under 64 characters — is persisted byte-for-byte into a column `db.ts` documents
as never garbage-collected, surviving project deletion and force-reinstall.

`redactQueryValues` classifies a segment with no `=` as a NAME and keeps it up to
`QUERY_NAME_MAX = 64`. Every common credential format on the web is shorter than that bound: a GitHub
PAT is 40 characters, an AWS access key id 20, a Stripe secret about 32, a session id 26–32, a UUID 36.
The bound catches a JWT, and only its tail.

Purpose — and this is the part that makes it a blocker rather than a documented residual. The residual
IS disclosed in the source (T-01-31 is named at `observations.ts:57-62`), so it is named rather than
hidden. But `observations.spec.ts:128-140` is the only case for the bound and it uses a name of
`QUERY_NAME_MAX + 40` — the one length at which truncation is visible — so no test in the file can go
red on it, while `schema.spec.ts:39-46` was rewritten in the same batch to assert the containing claim
is "NOW TRUE". The verifier's phrase for that combination is exact and it is the thing being closed
here: **an unfalsifiable residual under an upgraded claim.** Whatever policy the operator picks, the
test must be able to fail.

Output: an operator decision on record, that decision implemented in the write path, one executed case
per credential format, and a T-01-21 paragraph that claims nothing wider than what runs.

**Why the policy is a `checkpoint:decision` and not a planner choice.** The operator's UAT decision of
2026-08-21 was "keep parameter NAMES, redact VALUES", and a bare segment is *syntactically* a name —
so the code is a faithful reading of the decision, which is precisely why closing it needs the decision
re-opened rather than reinterpreted. Every way out costs a different analytic signal: dropping bare
segments loses `?debug` and `?nocache`, which are real feature-flag signals on bundle URLs; tightening
the bound keeps short flags and still passes a short credential; an allowlist keeps exactly what was
enumerated and redacts an unknown-but-legitimate flag. `REVERSIBILITY_GATES` is on and this changes
what is written into a durable column, so it carries `gate="blocking-human"`: `mode: yolo` with
`auto_advance: true` would otherwise auto-select the first option of an ordinary blocking decision.

**Why wave 10, serialised behind 01-09, when `files_modified` overlap with the other new plans is
zero.** Same reason plan 01-09 recorded, and it applies with more force now. Every one of the five new
plans deliberately breaks the shared working tree to prove its gate can fail — this plan reverts the
`eq === -1` branch, 01-11 reverts a head redaction and a path redaction, 01-12 plants outbound calls
into `hooks/passive.ts` and `packages/engine/src/pipeline.ts`, 01-13 plants an `e.message` render into
a real store module, 01-14 mutates the live tracer — and every one of them asserts the WHOLE suite is
green. Run concurrently, one plan's mutation window makes another's whole-suite assertion fail for an
unrelated reason, intermittently and misattributed to whichever plan happened to read the tree at the
wrong moment. A phase whose entire subject is gates that can fail honestly cannot afford a gate that
fails dishonestly. `depends_on: [01-09]` is a SEQUENCING edge, not a code dependency — recorded here in
words so nobody reads the empty file overlap and "optimises" it back into a shared wave.

**Why there is no leading `type="tracer"` task.** `TRACER_MODE` is on. The end-to-end path this plan
affects is already wired and already has a live tracer — `scripts/phase1/tracer-e2e.sh`, run three
times in plan 01-07 including a committed mutation run. This plan changes one branch inside a function
that path already crosses; the tracer that would prove it is plan 01-14, which runs it live once both
redaction plans have landed. Stated as the exception rather than forcing a tracer that would re-prove
a wired path.

**Why the CORE-11 requirement split lands HERE, in wave 10, rather than at the end of the phase.**
Plan 01-12 owns the outbound gate, and a plan must declare the requirement it enforces in its own
frontmatter — that is what a verifier reads. `REQUIREMENTS.md`'s CORE-01 is the non-async-handler
requirement and says nothing about outbound traffic, so a 01-12 that ships declaring `CORE-01` carries
the exact "one id, two meanings" defect the split exists to remove, in the one place it does the most
damage. Opening the id costs nothing now and is an eight-file cleanup later. The SOURCE half of the
retag — the gate's own header and failure text — deliberately does NOT come here: plan 01-12 rewrites
that file wholesale in wave 12, and two plans editing one paragraph two waves apart is how the second
silently reverts the first. So the ledger moves to the front and the source strings move with the
rewrite that is already happening.

**What this plan deliberately does NOT do.** It does not touch userinfo, `;` path parameters or
path-embedded tokens — those are WR-11, they need a different decision about how much of the non-query
URL to keep, and they are plan 01-11's subject. It does not touch `scripts/phase1/tracer-e2e.sh`;
the live proof of everything both redaction plans land is plan 01-14, run once rather than twice. It
does not touch any row already on disk: P8-D1 settled that at a blocking-human checkpoint on
2026-08-21 with a measured zero, and the population is closed by construction.

  <options>
    <option id="redact-bare">
      <name>Treat a bare segment as a VALUE WITH NO NAME and redact it (RECOMMENDED)</name>
      <pros>
        Closes the hole completely and by CONSTRUCTION rather than by a bound: no length of bare
        segment survives, so no future credential format can slip under a number. It is the reading of
        the operator's own decision that matches its words — the decision kept parameter NAMES, and a
        bare segment has no name. Keeps the parameter count, the order and the empty-segment
        behaviour, so the stored URL still shows how many parameters the endpoint took. One branch,
        the smallest diff of the three, and trivially idempotent because the replacement contains no
        `=` and is itself replaced on a second pass.
      </pros>
      <cons>
        Loses the bare FLAG as an analytic signal: `?debug`, `?nocache` and `?prod` become
        `<redacted>`, and a bundle URL's feature flags are a genuine signal about the target's build.
        Contradicts the existing spec case at `observations.spec.ts:76-80`, which must be amended with
        the reason recorded rather than deleted.
      </cons>
    </option>
    <option id="tighten-bound">
      <name>Keep bare segments but bound them at a length no credential fits</name>
      <pros>
        Keeps every short flag name intact — `debug`, `v`, `nocache`, `prod` are all well under any
        workable bound — so the analytic signal survives untouched. Smallest behavioural change for
        the URLs that actually appear in practice.
      </pros>
      <cons>
        It is a BOUND, not a rule, so the residual survives in kind: a credential shorter than the
        bound still reaches the column, and picking a number is picking which credentials are
        acceptable to keep. At 16 an AWS access key id (20) is caught and a 12-character key is not;
        anything low enough to be safe truncates legitimate long flag names such as
        `disableAnalytics` (16) or `enableExperimentalFeature` (25) into an ambiguous prefix that
        reads as a real name. Requires a second exported constant so a named segment can keep 64 while
        a bare one does not, which is a second number for a future reader to reconcile.
      </cons>
    </option>
    <option id="allowlist">
      <name>Retain only bare segments on an explicit allowlist and redact every other</name>
      <pros>
        The only option where the RETAINED set is closed and every retention is a deliberate act: what
        survives is what somebody enumerated, and adding to it is a visible two-place edit like the
        column allowlist in `schema.spec.ts`. Keeps the flags that matter and is immune to length
        entirely.
      </pros>
      <cons>
        An unknown-but-legitimate flag reads as `<redacted>`, which is a silent analytic loss that
        looks identical to a caught credential. The allowlist is authored, so it inherits the
        maintenance cost and the drift risk of every authored list, and Phase 1 has no corpus of real
        bundle-URL flags to derive it from — it would start as a guess.
      </cons>
    </option>
  </options>
