<objective>
Close CR-13 at the seam: read a conditional, `??` or `||` INITIALIZER the same way the key site already
reads the identical expression, and correct the two registry clauses it falsifies against the code.

Purpose. `const k = b ? "requests" : "net"; sdk[k].send(req)` reports nothing. That is ONE HOP, with
the literal written out in full, on both branches of a two-branch operator this gate resolves at four
other positions. The verifier put it first for a reason: **it is the round-3 blocker's own shape
standing one level over, and it is named by none of the seven measured silences.** It is not two hops
of key, not a function boundary, not a parameter, not a loop binding, not a destructured plain literal,
not an inverted binding, and not an operator around a GLOBAL receiver — this is an SDK receiver, and
the SDK operator is the one wave 25 closed.

**The mechanism, read off the code rather than off the finding.** `keyReceiver` performs the operator
descent INLINE, at the key site, through `operatorReceiver` and `operatorOperands`. `collect`'s
declaration branch does not: `bindString` requires a bare string literal after `unwrap`, and
`isAssembledKey` answers false for a `ConditionalExpression`. So the name lands in neither
`constStrings` nor `assembledNames`, and the key lookup answers "not a receiver". The fix is the
descent the key site already performs, applied where the name is BOUND.

**Every twin of the identical conditional already reports**, and that asymmetry is the finding rather
than a preference. The inline key produces `outbound-send`; the member name and the module specifier
both produce `outbound-unanalysable` through `literalOf` two functions away; the global key produces
`outbound-unanalysable`. Only the SDK receiver key bound through an initializer is silent.

**Two registry clauses are falsified word for word and both ship into the ledger.** `constStrings`
claims a key resolves when ANY string literal the name is bound to anywhere in the file names an
outbound receiver. `literalsOf` claims it reads every literal a name carries, so ANY of them naming a
receiver reports. `k` carries `"requests"`. Neither reports. Both rows are green because both probes
use a plain literal binding — **CR-08's defect, a clause whose stated reach exceeds its probe's,
reappearing inside the mechanism built to remove it.** The rows are corrected here, against the code,
in the same commit as the widening, and each corrected clause carries a `BranchProbe` per branch it
names so wave 29's vocabulary guard can see it.

**Wave 29 is a hard prerequisite.** It corrected both clauses to their measured pre-widening reach,
preserved the falsified universals with a dated marker, and named this wave as the owner. This plan
must re-add the branch-naming phrase AND its probe in the same commit as the code, or the row stays
red. That is deliberate: it makes this widening provable at branch granularity.

**SEVERITY, STATED PLAINLY AND NOT INFLATED.** Nothing leaks and nothing leaked. No outbound call
exists in any non-spec source under either root, the gate runs green over the real tree inside a
1200-test suite, and `check:bundle` reports the shipped bundle's entire import set as one specifier,
`crypto`. CR-13 is PROSPECTIVE blindness in a test-only gate — a call site somebody writes next year
that the gate would stay green on.

Output: a receiver key bound through an operator initializer that reports exactly as its four twins
do, two corrected clauses read off the branches, and the residual stated as what the measurement found.

**Why wave 30, and why serialised.** The widening must be measured against the gate as wave 29 left it,
including the `branches` field the corrected rows have to populate. It also plants three deliberate
mutations in shared files, which needs a quiet tree.

**What this plan deliberately does NOT do.** It does not touch the logical-assignment collector gap
(CR-12, wave 31) or the operator around a GLOBAL receiver (CR-11, wave 32). It does not flip CORE-11's
checkbox — wave 32 owns that. It does not touch `packages/backend/src/store/*`, `tests/pins.spec.ts`
or `scripts/phase1/tracer-e2e.sh`. It modifies no plan 01-01 through 01-29, and no
`01-VERIFICATION.md`, `01-REVIEW.md` or `01-UAT.md`.
