## Success-criterion correction (recorded, not silent)

ROADMAP Phase 1 success criterion 6 currently reads: *"A CI gate fails the build if the backend bundle imports
any Node built-in."* **As literally worded, that criterion fails a correct DefMiner and must not be
implemented.** Three measured facts:

1. `@caido-community/dev@0.1.7` builds the backend with `external: [/caido:.+/, "sqlite", ...builtinModules]`.
   Node 26's `builtinModules` has 66 entries, so every built-in is externalised silently.
2. Caido's QuickJS resolves **some** of those and hard-fails on others. Verified in this repo's own capability
   probe (`results/runs/20260820T121824Z-31596/raw/capabilities.json`): `os`, `path`, `fs`, `sqlite`,
   `caido:http`, `crypto`, `buffer`, `string_decoder`, `url`, `events` all load; `util`, `stream`, `zlib`,
   `process`, `perf_hooks`, `qjs`, `llrt:qjs` and **`caido:crypto`** all fail with
   `could not load module`.
3. A real, working, already-built Phase 0 backend bundle emits `import { readFileSync } from "fs"` and
   `import { createHash } from "crypto"` on its first two lines. The native hash is not optional — DET-07
   forbids the JS loop that Phase 0 measured at 187 ms/MB against 0.34 ms/MB native.

**The corrected criterion, implemented by this plan:** *"A CI gate fails the build if the backend bundle
imports any module specifier outside the allowlist Phase 0 proved loadable inside Caido."* This is strictly
stronger than the original in the direction that matters — the original would not have caught `zlib`, `util`,
`stream` or `caido:crypto` at all, since it treats built-ins as one undifferentiated set and `caido:crypto` is
not a built-in. The ROADMAP text is updated in the same commit so the phase verifier checks the rule that is
actually correct.
