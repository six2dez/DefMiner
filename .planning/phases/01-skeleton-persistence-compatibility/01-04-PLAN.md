<objective>
Build out the persistent layer from the two tables the tracer proved: add `analyses` and `settings` behind a
forward-only migration ladder tested against a populated database, add the reads and the corpus-version cache
that let a second sighting skip re-analysis, add a bounded retention sweep, and add a static gate that makes
the SQL discipline mechanical rather than cultural.

Everything this plan does to `artifacts.ts` and `observations.ts` is **additive**. Neither `upsertArtifact`
nor `recordObservation` changes signature, and migration step v1 is not touched. That is deliberate: an
earlier draft had this plan remove a `url` parameter while plan 01-03 rewrote the only caller in parallel,
which is a contract break across two plans that no `files_modified` overlap check can see, because the shared
mutable resource is a function signature rather than a file.

Purpose: this layer has no transaction primitive and its failure mode is silent-then-fatal. `BEGIN` does not
span `exec` calls while every statement still returns SUCCESS, so code that looks transactional passes every
test and provides zero atomicity. A multi-statement `exec` that fails strands an open write transaction on an
unreachable pooled connection and the database is locked for writes until the plugin restarts.
`last_insert_rowid()` is unusable on that pool, so a row a later statement must reference is addressed by a
natural key or not at all. Every one of those was measured, not inferred, and each one removes an option most
SQLite code takes for granted.

Output: four tables all keyed on `project_id`, every mutation a single-statement idempotent upsert, and three
gates — a schema gate that reads key ordinals rather than DDL text, a migration gate that runs forward over
seeded data, and an AST gate over every SQL string and every bind call site in the package.
</objective>

## Flagged Planner Assumptions (edge-probe `unclassified`, unresolved)

- **CORE-08 (unclassified)** — assumed: "never re-analysed" means no new `analyses` row is created for a
  `(project_id, sha256, detector_set_hash)` that already has one in a terminal `scan_state`; the observation and
  the `seen_count` still update, because the same bytes appearing again is real information even when the
  analysis is cached. Assumed budget: `CACHE_HIT_RATE` is the pessimistic 0.40 placeholder, never the measured
  within-session 0.6304, because `CACHE_HIT_RATE_CROSS_DAY` is null with status `inconclusive` (open Broken
  Window #6, revisit after 2026-09-03).
- **STORE-04 (unclassified)** — assumed: "detector-corpus version" is a content hash of the rule corpus, stored
  as an opaque string column `detector_set_hash`, and Phase 1 writes a fixed sentinel because no corpus exists
  until Phase 3. The sentinel must be a value Phase 3 can distinguish from a real hash.
- **STORE-05 (unclassified)** — assumed: "run forward on upgrade" means monotonically increasing integer steps
  applied in order from `PRAGMA user_version`, with no down-migrations at all, and "tested against a populated
  database" means seeded rows survive the step and remain readable, not merely that the step exits 0.
- **STORE-06 (unclassified)** — assumed: retention bounds BOTH a maximum row count per table per project and a
  maximum age, whichever binds first, with the sweep itself bounded so it can never become the long synchronous
  slice it exists to prevent. Assumed: Phase 1 sets conservative defaults in `settings` rather than deleting
  aggressively, because there is no UI to change them until Phase 5. Assumed: "bounds database growth" requires
  the sweep to be SCHEDULED, not merely available — an uncalled function bounds nothing — and the schedule is
  the consumer loop (P1-D7), owned by plan 01-03, because this runtime has one thread and `setTimeout` is the
  yield primitive, so a long-lived background timer would be a design smell rather than a scheduler.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| target-controlled strings -> SQL bind values | URL, content type and status originate with the target and reach a shared plugin-global database |
| project A's data -> project B's queries | `sdk.meta.db()` is ONE database for the plugin across every project; project isolation is an access-control boundary here, not a data-modelling nicety |
| plugin database -> the filesystem | The file lives in Caido Data, is never GC'd, survives project deletion and force-reinstall, and can be copied off the machine |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-01-19 | Tampering | every SQL string in `packages/backend/src/store/` | high | mitigate | Positional binding only via prepare-then-run with spread parameters, enforced by the `sql-discipline.spec.ts` AST gate rather than by review. | T-01-21 | Information Disclosure | the plugin database file itself | high | mitigate | Enforced by ABSENCE plus a column allowlist: no column in any table can hold a body, a header, a cookie or a secret. A stolen copy of the file is a list of URLs, digests and byte counts, not a credential dump. `value_raw` and `path_key` are explicitly excluded and the schema gate fails if either appears. |
| T-01-22 | Denial of Service (disk) | unbounded growth in Caido Data | medium | mitigate | `sweepRetention` bounds both row count and age per project, with a per-pass cap so the sweep cannot itself become a long synchronous slice, and cascade deletion by natural key so orphans cannot accumulate. **The mitigation is only real once it is invoked**, and the invocation is plan 01-03's consumer loop at one bounded pass per `RETENTION_SWEEP_EVERY_N` processed artifacts (P1-D7) — this plan owns the behaviour, 01-03 owns the schedule and carries the truth and acceptance criterion proving a running plugin actually trims. | T-01-23 | Denial of Service | a failed multi-statement `exec` | high | mitigate | No data write is ever a multi-statement `exec`. DDL is batched only because every statement is `IF NOT EXISTS` and therefore cannot fail on a re-run. The measured consequence of getting this wrong is an open write transaction stranded on an unreachable pooled connection and a database locked for writes until the plugin restarts, with no recovery path in the plugin API. |
