<objective>
Make the plugin correct across the two lifecycle events that can silently corrupt everything else — a project
switch and a restart — and make the max synchronous slice a number measured from OUTSIDE the process rather
than asserted from inside it.

Purpose: `sdk.meta.db()` is one database for the plugin across every project, so a project switch that does not
cancel in-flight work and swap the active id writes client A's artifacts into a session where the operator is
looking at client B. The SDK types the project as `Project | null`, and null is a real case — it is what
happens when the user deletes the currently selected project — so it is a branch, not a defensive check.

And success criterion 3 cannot be measured from inside the plugin. A starved thread cannot report that it is
starved, and this runtime has no scheduler or memory introspection at all: `perf_hooks`, `process` and
`llrt:qjs` all fail to load. The measurement must come from an external caller polling an RPC on a fixed
interval while load runs, with jitter in the observed response times as the signal — which is exactly the
apparatus Phase 0 already built and which is reused here rather than reinvented.

Output: lifecycle handling with the null branch as a first-class state, an in-memory counter surface that
Phase 2 can build on without retrofitting **and that the hook and consumer actually feed**, and a recorded
external measurement of the max slice and the RPC latency distribution under a 200-chunk load.

The counter surface is introduced here but its producers were written two waves earlier, so this plan owns
both ends of that wire. A `telemetry.ts` with an unwired `recordSlice` would leave `getStatus().maxSliceMs` at
zero, and task 3's gate deliberately fails on a zero rather than reading it as a perfect score — so the defect
would surface only after a live Caido run and a 200-chunk load, at the most expensive moment in the phase.
</objective>

## Flagged Planner Assumptions (edge-probe `unclassified`, unresolved)

- **CORE-09 (unclassified)** — assumed: "cancel in-flight work" means the current artifact's walk aborts via its
  signal and its analysis row is left in a non-terminal state for Phase 2's ERR-02 to reconcile, NOT that the
  row is deleted. Assumed: "never leak results across projects" is satisfied by cancelling, draining the queue,
  resetting the memoised database handle and swapping the active id before any further write — and by every
  table already carrying `project_id` in its key. Assumed: entries already in the queue when the change fires
  belong to the OLD project and are discarded rather than re-attributed, because their request ids were admitted
  under the old scope.

## Scope boundary held deliberately

Phase 2 owns ERR-01 through ERR-04 and OBS-01 through OBS-03: per-artifact error isolation, stale-job detection,
the health surface, the degradation vocabulary and the diagnostics export. This plan must not pre-build any of
them. What it must do is leave the seam open, and that obligation is narrow and cheap: the counters must EXIST
and be reachable, or Phase 2 has to retrofit them through code that has already been reviewed. Concretely, a
`scan_state` row left `running` by a killed process is NOT reconciled here — the column exists, and reconciling
it is 02-02's job. Phase 1's restart obligation is only success criterion 4: artifacts persist and the plugin
re-attaches.
