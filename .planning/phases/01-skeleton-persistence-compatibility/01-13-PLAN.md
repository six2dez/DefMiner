<objective>
Close the third finding folded into UAT gap 2, and settle the requirement-ledger collision the verifier
flagged for the record.

`error-redaction.spec.ts` cannot see `e.message`. All three catch rules bottom out in `isRefTo`, which
is `ts.isIdentifier(node) && node.text === name` — so the binding must appear as a BARE IDENTIFIER.
Reach through it, cast it, or copy it, and the rule is gone. Executed, not argued:

    catch(e){ return e.message; }                []      catch(e){ return "x: " + e.message; }   []
    catch(e){ return `x: ${e.message}`; }        []      catch(e){ return String(e.message); }   []
    catch(e){ return e.toString(); }             []      catch(e){ return JSON.stringify(e); }   []
    catch(e){ return String(e as Error); }       []      catch(e){ return `${e as any}`; }       []
    catch(e){ const x = e; return String(x); }   []      catch(e){ return [e].join(""); }        []
    function fin({ error }: {…}) { … }           []      (rule 4 needs ts.isIdentifier(param.name))

Purpose. `e.message` is not an exotic spelling — it is *the* spelling. And in this codebase
specifically, TypeScript types a catch binding as `unknown`, so anything richer than `String(e)`
requires a cast: `String(e as Error)` and `(e as Error).message` are the forms the compiler pushes an
author toward, and the gate is blind to both. That matters because `schema.spec.ts:62-70` justifies
keeping the `analyses.error` column in the T-01-21 allowlist ON THE STRENGTH OF THIS GATE, the column
is durable for 90 days in a file `db.ts` documents as never garbage-collected, and the gate's own
comment names Phase 2's ERR-02/ERR-04 authors as the people who "will read the gate to learn what is
already guaranteed". They will write `error: (e as Error).message` and ship it green.

The second half is a ledger correction, not code. `01-09-PLAN.md`'s prohibition carries
`requirement_id: CORE-01`, and `REQUIREMENTS.md:36`'s CORE-01 is the non-async-handler requirement — it
says nothing about outbound traffic. One id, two meanings. This phase already has the precedent for the
fix and the operator already chose it: at UAT test 2 the same shape in STORE-01 was settled by
re-scoping the requirement and opening STORE-08 for the part that had no owner.

Output: a gate that follows the binding instead of matching it, with all ten executed shapes as
fixtures; and a requirement ledger in which every gate enforces the requirement it names.

**Why wave 13, serialised behind 01-12.** The same reason every plan from 01-09 onward has recorded,
and it binds here twice over: this plan plants an `e.message` render into a real store module while
asserting the whole suite is green, and it edits `outbound-prohibition.spec.ts`, which plan 01-12
rewrites. The second is a real `files_modified` overlap the wave guard would catch on its own; the
first is the one it cannot see, and it is why 01-10, 01-11 and 01-12 are also serialised despite zero
overlap between them. Run concurrently, one plan's mutation window makes another's whole-suite

already-shipped code and task 2 edits three ledger documents; there is no path through the stack to

**What this plan deliberately does NOT do.** It does not widen the gate's SCOPE beyond
`packages/backend/src/store/`. Boundary 1 of the gate's header records that decision as T-01-37
