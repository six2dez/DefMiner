<objective>
Build the three frontend state pieces the tables sit on: a typed client over the RPC that checks the
contract version, a bounded windowed store that pages by cursor and refetches short pages, and a
coalescer that turns a flood of invalidation summaries into at most two reactions a second and none
at all while the operator is mid-triage.

Purpose: `05-UI-SPEC.md`'s table contract is a set of properties that are all about *not* doing the
obvious thing — never ship the whole result set to the view, never sort the window, never re-order
under a selected row. Each of those is a correctness property with a failure mode that looks like a
feature: a client-side sort over a two-thousand-row window sorts a subset and presents it as the
whole set, and a row shifting under the cursor mid-triage is how an operator marks the wrong finding
as a false positive, which writes durable state.

Output: `api/client.ts`, `stores/inventory.ts`, `stores/coalescer.ts` and their specs.
</objective>

  <files>packages/frontend/src/stores/inventory.ts, packages/frontend/src/stores/inventory.spec.ts</files>
  <read_first>
    - packages/frontend/src/api/client.ts — as written in task 1

    - packages/backend/src/store/reads.ts — the sort keys and the single filter column available per table, and the short-page semantics of the scanned and exhausted fields
    - .planning/phases/05-workspace-operator-workflow/05-UI-SPEC.md § "Data & Interaction Contract" — the whole table-contract table, especially the in-memory window row and the sorting-and-filtering row with its stated reason
    - .planning/phases/05-workspace-operator-workflow/05-RESEARCH.md § "O-01" — the short-page paragraph and the response shape it forces
  </read_first>
  <behavior>
    - Loading the first page requests no cursor and stores the returned rows and next cursor.
    - Loading the next page sends the stored cursor and appends the returned rows.
    - When appending would exceed the window bound, the oldest resident rows are evicted so the resident count never exceeds the bound.
    - Scrolling back to an evicted range refetches it by cursor rather than serving stale rows.
    - A response with fewer rows than the page size and a next cursor present triggers another request from that cursor, and repeats until a full page is assembled or the response reports the cursor exhausted.
    - A response with fewer rows than the page size and the cursor exhausted ends the loop and marks the list complete.
    - Changing the sort key, the sort direction, or the filter discards the whole window and refetches from the first page.
    - The store exposes no operation that reorders resident rows.
    - Selecting a row records the selection; clearing it clears the selection; the panel-open flag is independent of the selection.
    - The reachable count is fetched alongside the first page and is what the filtered-empty copy interpolates.
  </behavior>
  <action>
    A store holding: the resident rows, the next cursor, the exhausted flag, the current sort key and
    direction, the current single-column filter, the selected row key, the panel-open flag, and the
    reachable count.

    The window bound is a named constant with the design contract's rationale: it bounds the
    renderer's memory the way the backend queue bounds its own. Eviction is forward-scroll only —
    when a new page pushes the resident count over the bound, drop from the far end, and record the
    dropped range's boundary cursor so a scroll back can refetch it.

    **The short-page loop** is the part that exists because of the bounded candidate window on the
    backend. A page can return fewer rows than requested while more exist, because its candidate
    window was filtered out. Loop from the returned cursor until a full page is assembled or the
    response reports exhaustion, with a bounded number of iterations declared as a named constant so
    a pathological filter cannot spin — and when that bound is hit, stop and record it as a distinct
    state rather than pretending the list ended.

    **No client-side sort exists in this module in any form**, including a computed property that
    orders rows for display. Sorting changes the request. The reason is in the design contract and is
    worth restating in the module header: sorting the resident window would sort a subset and present
    it as the whole set, which is a correctness defect that looks like a feature.

    Selection and panel state live here rather than in a component because the coalescer reads them
    to decide whether it may react at all.

    `inventory.spec.ts` drives the store against a stub client, covering every behaviour. The
    short-page loop and the eviction-then-refetch case are the two that would otherwise be discovered
    by an operator scrolling a filtered list.
  </action>

  <read_first>

    - packages/frontend/src/api/client.ts — `subscribeInvalidation` and its stop handle

    - .planning/phases/05-workspace-operator-workflow/05-RESEARCH.md § "Architecture Patterns" Pattern 4, § "Common Pitfalls" P-04, and § "Don't Hand-Roll" (the debounce row)
  </read_first>
  <behavior>
    - One summary arriving with nothing selected and the panel closed produces one reaction, after the trailing window elapses and not before.
    - Twenty summaries arriving inside one simulated second produce at most two reactions.
    - Summaries arriving while a row is selected produce zero reactions, and their changed counts accumulate into the pending count.
    - Summaries arriving while the panel is open produce zero reactions, independently of whether a row is selected.
    - Clearing the selection does not by itself trigger a reaction; the accumulated count stays pending.
    - Invoking the refresh action applies the pending count and resets it to zero.
    - Advancing the simulated clock by any duration with a pending count and nothing selected does not apply the pending count.
    - Summaries for different categories accumulate separately in the pill's breakdown while sharing the single reaction-rate cap.
    - A summary whose project does not match the current project is discarded.
    - Stopping the store removes the subscription; a summary emitted afterwards changes nothing.
  </behavior>
  <action>
    A store that owns the subscription and the pending counts.

    Use the pinned composable library's debounce and throttle helpers rather than hand-rolled timer
    bookkeeping — hand-rolled timers leak across unmounts, and the leak shows up as duplicated
    refreshes on the fourth project switch, which is exactly the kind of late silent failure the
    research's don't-hand-roll list is about. Compose them: a trailing debounce at the window
    duration, behind a throttle gate at the reaction cap, both declared as named constants carrying
    the design contract's numbers and their reasons.

    **The suppression rule is checked first, before the debounce.** While a row is selected or the
    panel is open, a summary accumulates into the pending count and returns immediately — it does not
    enter the debounce, because a debounced reaction that fires just after the operator selects a row
    is the same defect arriving late.

    The pending count never auto-applies. Design decision D4 is explicit: auto-applying reintroduces
    exactly the row-shift-under-cursor risk the coalescing rule exists to remove. It applies on the
    refresh action and on the page's re-entry hook, and nowhere else. Do not add an inactivity timer.

    Discard summaries whose project does not match the current one — a project switch and an in-flight
    event race, and applying the wrong project's count is a visible wrong number.

    Expose `stop()` that calls the subscription's stop handle, and require the mounting component to
    call it on unmount. Assert that requirement in the spec rather than trusting it.

    `coalescer.spec.ts` uses fake timers throughout. The twenty-events case and the
    advance-the-clock-with-a-pending-count case are the two that prove the two halves of the
    contract; a passing rate cap must not be able to mask a broken suppression, so the suppression
    cases assert zero reactions rather than fewer reactions.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| backend RPC response -> frontend store -> rendered row | Every row the store holds carries target-controlled bytes; the store is where they are held, not where they are sanitised |
| backend event -> frontend reaction | An unbounded reaction rate is a self-inflicted denial of service on the renderer |
| project switch -> in-flight event and in-flight page request | Two projects' data can be resident at once if the boundary is not enforced |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-38 | Denial of Service | listener leak multiplying reactions across project switches | high | mitigate | The subscription's stop handle is returned by the client, owned by the store, and asserted removed by a test that emits after stopping (tasks 1, 3) |
| T-05-39 | Denial of Service | an event flood driving unbounded re-renders on a ten-thousand-row surface | high | mitigate | Trailing debounce behind a throttle gate at the stated cap, asserted at twenty events per simulated second (task 3) |
| T-05-40 | Tampering | a row shifting under the cursor mid-triage, so the operator writes durable state against the wrong row | high | mitigate | Suppression is checked before the debounce, asserted as exactly zero reactions in two independent tests, and the pill never auto-applies (task 3) |
| T-05-41 | Information Disclosure | one project's rows resident while another is active | high | mitigate | Summaries carrying a foreign project id are discarded, and a sort or filter change discards the window entirely (tasks 2, 3) |
| T-05-42 | Tampering | a stale bundle misreading a changed return shape as valid rows | medium | mitigate | The contract-version check is a hard state that suppresses page calls rather than a warning (task 1) |
| T-05-43 | Information Disclosure | a raw backend rejection string reaching the UI with a host in it | medium | mitigate | Failures cross as DefMiner-authored reason codes; a test asserts the returned reason shares no substring with the stub rejection (task 1) |
