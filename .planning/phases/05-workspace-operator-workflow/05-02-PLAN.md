<objective>
Widen the static SQL discipline gate to cover the four shapes it is measurably blind to — all four
of which are the natural spellings for what Phase 5 is about to write — and convert the two
research assumptions that the query design rests on into executed measurements.

Purpose: `sql-discipline.spec.ts` is the strongest invariant in the backend, and
`05-RESEARCH.md § O-01` executed its own exported `auditSource` against twenty-four candidate
statements and found five silent shapes. Four of them (CTE, `INSERT … SELECT`, unscoped subquery,
unscoped `UNION` arm) are exactly what an aggregate, an audit write and a suppression filter look
like. The file's own header states the rule this plan follows: a gate whose failure path has never
run is a gate nobody has tested.

Output: a gate that sees the shapes this phase writes, and two measurement specs whose numbers the
query design and the export contract can be built on.
</objective>

    Add five rules to `auditSource`, named `cte-unscoped`, `insert-select`, `unscoped-subquery`,
    `unscoped-union-arm` and `fragment-composition`, each with a `detail` string that says what went
    wrong and why the driver or the schema makes it dangerous, in the voice of the nine existing
    `detail` strings.

    The two mechanisms behind the current silences are both in the source and both must change.
    First, `isMultiRowStatement` accepts only `SELECT`, `UPDATE` and `DELETE`, so `statementKind`
    returning `"WITH"` for a CTE and `"INSERT"` for `INSERT … SELECT` takes both out of the
    project-scoping check entirely. Extend the scoping check to cover a `WITH` head and to cover an
    `INSERT` whose body contains a `SELECT` clause, rather than widening `isMultiRowStatement`
    itself — the existing rule's name and message are about multi-row reads and writes, and an
    upsert must keep passing.

    Second, `concatenated-sql` only inspects `+` operands that are *themselves* SQL-looking string
    literals, so composing named fragments is invisible. `fragment-composition` must fire on three
    forms: a binary `+` chain any of whose operands is an identifier AND whose result is passed to
    `prepare`/`exec`/`run`/`get`/`all`; a template literal whose head is not SQL-looking but which
    has an interpolation and reaches the same sinks; and an `Array.prototype.join` call whose array
    literal contains a SQL-looking string. Detect at the sink so a plain string concatenation
    unrelated to SQL does not trip it.

    `unscoped-subquery` and `unscoped-union-arm` both need the statement split before they can be
    checked. Split on top-level `UNION`/`UNION ALL`/`INTERSECT`/`EXCEPT` for the arm rule, and
    extract balanced-parenthesis subquery spans that begin with `SELECT` for the subquery rule, then
    apply the existing project-scoping predicate check to each piece independently. Tables in
    `SETTINGS_TABLES` stay exempt in every piece, exactly as they are today.

    Every new rule gets a paired positive/negative fixture in the existing
    `describe("the gate's own failure paths")` block, using the probe texts from
    `05-RESEARCH.md § O-01` verbatim so the fixture and the measurement are the same statement.
    Extend the non-vacuity assertions: the named module list, the descent proof and the
    found-something-to-audit proof all stay, and add an assertion that the rule-name set the gate
    can emit has grown to fourteen and that each of the five new names is reachable from at least
    one fixture.

    allowlisted fragment builder cannot earn an exemption because the gate does not see it today —
    the honest sequence is to widen first and only then consider a narrow entry, and plan 05-06 uses
    the fixed literal matrix instead, so no entry is needed at all.

    2. The same row-value cursor against a mixed-direction index `(… DESC, … ASC)` — assert the
       plan DOES report a temp b-tree, so the direction rule is proved by contrast and not merely
       asserted. This is the "mixing an index direction against the ORDER BY direction costs a
       sorter" finding.

       an outer `NOT EXISTS` filter and an outer `LIMIT 100`, against a fixture where every
       candidate row is filtered out. Assert the plan is a CO-ROUTINE over the inner query with a
       correlated scalar subquery, and assert a bounded scanned-row count: instrument by counting
       rows the inner query can yield, and assert that count is at most the inner limit regardless
       of how many rows the partition holds. Run the same assertion at two partition sizes and
       assert the scanned count does not grow between them — selectivity independence is the
       property that matters, not any single number.

    Also assert the correctness property the cursor exists for: seeded with a deliberate tie block
    (several rows sharing `last_seen_at`), a cursor positioned mid-block returns the remainder of
    the block and then continues, with no row returned twice and no row skipped, across three
